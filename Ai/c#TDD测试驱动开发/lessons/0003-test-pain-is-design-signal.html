C# TDD 课程 · 第 3 课

测试难写，是谁的问题？疼痛是代码在报警——找到接缝，把依赖变成可以替换的东西

回顾一下你在 TddLab 里写过的东西：XorChecksum、Parse——测试从来都是五分钟搞定，你有没有想过为什么一直不疼？因为它们是纯函数：输入进、输出出，中间不碰世界。而你的日常工作不是纯函数——要开串口、要读时钟、要碰文件。这一课就讲：当测试开始疼，疼的不是测试，是代码在向你报警；TDD 的价值之一，是让报警在开发当下就响，而不是在评审或联调时。

先亲手疼一次

新需求：把帧加上校验字节后发到设备。你可能顺手就写成这样：

using System.IO.Ports;

public class FrameSender
{
    public void Send(byte[] frame)
    {
        using var port = new SerialPort("COM3", 9600);
        port.Open();
        port.Write(frame, 0, frame.Length);
    }
}

现在试着为它写一条测试——Send(new byte[] { 0x10, 0x02 }) 之后「发了什么」怎么断言？测试一跑就要开 COM3：没接设备就抛异常，接了设备就是对真实硬件说话。你会发现自己卡在三个问题上：

  • 没设备跑不了——测试需要整条硬件链路在场
  • 跑起来也断言不了——发出去的字节收不回来检查
  • 慢且脆弱——占着串口、受环境影响，CI 上更没法跑
本课核心 写不出测试，几乎从来不是测试的问题，也不是你水平的问题。是代码里藏着「你无法替换的东西」——new SerialPort(...) 这一行把行为焊死在了代码内部。Michael Feathers 给这种「能替换行为的落点」起了名字：接缝（seam）——代码中一个不改动它本身就能改变其行为的地方（《Working Effectively with Legacy Code》）。上面这段代码没有接缝，所以测试无处下手。

惯犯名单：哪些东西藏在代码里就疼

串口只是之一。看到这些写死在方法体里，你就可以预告「这测试会疼」：

隐藏依赖疼在哪
new SerialPort(...) / HttpClient / File.ReadAllText碰真实硬件、网络、磁盘
DateTime.Now / Stopwatch时间不等人的测试没法写、会闪红
new Random()不可复现
静态类、单例、Console全局状态，测试之间互相污染

共同点：它们都在方法内部自己制造自己的依赖，外部无人能换。解法不是换测试框架，而是把「制造依赖」和「使用依赖」拆开。

动手：让红灯逼出接口

这次反过来——不先写实现，先写测试，让 TDD 替你做这个设计决定。第一条测试长这样（先别管 IFrameChannel 哪来的，往下看）：

[Fact]
public void Send_appends_xor_checksum()
{
    var channel = new RecordingChannel();
    var sender  = new FrameSender(channel);

    sender.Send(new byte[] { 0x10, 0x02 });

    Assert.Equal(
        new byte[] { 0x10, 0x02, 0x12 },   // 校验字节 0x12 被追加在帧尾
        channel.LastWritten);
}

private class RecordingChannel : IFrameChannel
{
    public byte[] LastWritten { get; private set; } = Array.Empty<byte>();
    public void Write(byte[] bytes) => LastWritten = bytes;
}

RecordingChannel 是一个测试替身：它假装是通道，其实只把收到的字节记下来给你断言。要让这段编译通过，你不得不长出这两样东西——这就是红灯在工作：

public interface IFrameChannel          // 接缝：行为可以在这里被替换
{
    void Write(byte[] bytes);
}

public class FrameSender                // 纯逻辑：拼校验、写通道
{
    private readonly IFrameChannel _channel;

    public FrameSender(IFrameChannel channel) => _channel = channel;

    public void Send(byte[] frame) =>
        _channel.Write(frame.Append(Frame.XorChecksum(frame)).ToArray());
}

public class SerialFrameChannel : IFrameChannel   // 真硬件，只在组装时出现
{
    private readonly string _portName;
    public SerialFrameChannel(string portName) => _portName = portName;

    public void Write(byte[] bytes)
    {
        using var port = new SerialPort(_portName, 9600);
        port.Open();
        port.Write(bytes, 0, bytes.Length);
    }
}

从构造函数把依赖传进来，叫构造函数注入——接缝最常用的形态。跑测试：绿，全程没碰硬件。

停下来看看发生了什么：IFrameChannel 不是你「设计」出来的，是测试要求能替换通道，接口自己长出来的。而且长出来的东西顺带更好用——FrameSender 现在根本不知道串口的存在，同一个类换个实现就能走 TCP、写文件、接内存通道。这就是「TDD 倒逼设计」的全部机制：可测试的 = 低耦合的，测试疼就是耦合的体温计。

注：真的要用串口需给项目加 System.IO.Ports NuGet 包；但注意 SerialFrameChannel 在测试里根本不会被实例化——硬件代码装进去，不代表测试要跑它。你在 WPF/Prism 里用的 DryIoc 自动装配，做的就是这件事的自动化版本：按构造函数签名把实现塞进去。

检查一下手感

课后作业：让疼痛长出接缝

  1. 先清账（约 10 分钟）：第 2 课的 ToHexString 三圈还没做——先跑完（Fake It → 逼出 ToString("X2") → 逼出空格分隔），顺路把往返一致性 Theory 补上。
  2. 重头戏：在 TddLab 里为 FrameSender 跑完整 TDD——就写 Send_appends_xor_checksum 这条测试开局，让它逼出 IFrameChannel 和构造函数注入。第二条测试加 Send(Array.Empty<byte>()) 只写出校验字节 0x00——顺便体验 Theory 加一行就是一条新测试。
  3. 想一想（带回讨论）：XorChecksum 和 Parse 从来没让你疼过，为什么？用自己的代码说清「可测试的 = 低耦合的」这句话。

本课首选原著：Michael Feathers《Working Effectively with Legacy Code》——接缝概念的出处。这本书名义上讲遗留代码，实际是「怎么给没有接缝的代码开缝」的百科全书，等工作项目里改老代码时它就是主文本。图书页 · 构造函数注入的官方对照：Microsoft Learn — Dependency injection。
