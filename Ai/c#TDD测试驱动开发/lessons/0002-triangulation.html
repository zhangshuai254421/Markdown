C# TDD 课程 · 第 2 课

三角定位：让谎言退场一条测试只能钉住一个点，第二条测试才能逼出真代码

先承认第一课埋下的尴尬：GREEN 阶段如果你写的不是 XOR 循环，而是 return 0x12;——测试照样全绿，一秒都不少。一条测试分不清真代码和硬编码的谎言。这不是 TDD 的漏洞，而是它的一个核心预设：别指望一条测试检验一切，真正约束实现的是「下一条测试」。这一课讲的就是这个机制——三角定位（Triangulation），以及它顺手教会的 xUnit 参数化测试。

两个观测点，才能定一个位置

这个词来自测量学：只从一个观测点看目标，方向已知但距离未知；从两个点各测一次方位角，两条线的交点就是目标。Kent Beck 把这个隐喻搬进了 TDD（《TDD by Example》第 3 章）：

  • 一条测试 = 一个观测点 = 一条方位线。任何能「恰好满足它」的代码都能让灯变绿，包括谎言。
  • 第二条不同输入的测试 = 第二个观测点。同时满足两个例子的代码，几乎只能是真规则。

return 0x12; 骗得过 {0x10, 0x02} → 0x12，但骗不过 {0x7F} → 0x7F。谎言的寿命，由你下一条测试的到达速度决定。

Beck 的三种到绿策略

既然红灯必须变绿，那绿怎么来？Beck 在书里给了三种合法姿势，理解了它们，你对 GREEN 阶段的纪律就不再教条：

策略做法什么时候用
Fake It
明明白白做假		 直接硬编码返回测试期望的值 想先保持小步子；让下一轮测试来收拾它
Triangulation
三角定位		 刻意再加一个例子，用两条测试的「交集」逼出真实现 对规则怎么泛化心里没数、设计走向不明时
Obvious Implementation
显然实现		 实现已经很明显，直接写出来（测试仍然先行） 一眼能看到答案时——别为了仪式把三行代码拆成三轮

注意最后一条：TDD 不是让所有人永远走碎步。经验越多，Obvious Implementation 占比越高，Fake It 和三角定位是你没把握时的工具。Beck 自己也说三角定位他并不常用——它是保留给「设计看不清」时刻的精密仪器，不是每日仪式。

实战：把 Parse 从谎言逼成真代码

继续第一课的 FrameCodec 试验场。目标：解析十六进制帧字符串。第一圈，先允许自己撒个谎：

第 1 圈 · RED

[Fact]
public void Parse_single_byte_10()
{
    Assert.Equal(new byte[] { 0x10 }, Frame.Parse("10"));
}

第 1 圈 · GREEN，用 Fake It

public static byte[] Parse(string text)
{
    return new byte[] { 0x10 };   // 明明白白的假——但它绿了
}

红灯变绿。心里有点不舒服？很好，这个不舒服就是下一圈的燃料。有人会问：这不是自欺吗？——不是。Fake It 证明了一件事：你的测试通道是通的，测试真的在约束这个行为。现在收拾它：

第 2 圈 · RED，第二个观测点

[Fact]
public void Parse_single_byte_7F()
{
    Assert.Equal(new byte[] { 0x7F }, Frame.Parse("7F"));
}

跑测试——红了。硬编码 0x10 编不过 0x7F 这关。两个观测点都在了，交点只有一条线：把输入真的转换成字节。

第 2 圈 · GREEN，真实现登场

public static byte[] Parse(string text)
{
    string[] parts = text.Split(' ');
    var bytes = new byte[parts.Length];
    for (int i = 0; i < parts.Length; i++)
        bytes[i] = Convert.ToByte(parts[i], 16);
    return bytes;
}

注意：写这个实现时你没有多写任何没被测试要求的东西——空格分隔是例子带来的，Convert.ToByte(…, 16) 是两个例子共同指向的规则。这就是三角定位的味道：不是你更聪明了，是两条测试把空间挤得只剩正确答案。跑测试，绿。第一课作业里的 Parse("10 02")，这条实现顺手就满足了——可以再为它补一条测试确认。

REFACTOR：把例子收编成规则表

现在 Parse 有了三个例子，两条 [Fact] 有点啰嗦。xUnit 对「一条规则、多组数据」有专门的写法——[Theory]：

[Theory]
[InlineData("10",    new byte[] { 0x10 })]
[InlineData("7F",    new byte[] { 0x7F })]
[InlineData("10 02", new byte[] { 0x10, 0x02 })]
public void Parse_hex_string(string text, byte[] expected)
{
    Assert.Equal(expected, Frame.Parse(text));
}

[Fact] 是「一个具体案例」，[Theory] 是「一条规则、多组数据」——每行 InlineData 按书写顺序喂给方法形参，各自独立运行、独立报红（哪组数据失败，报告里说得清清楚楚）。这和三角定位是同一件事的两面：多例子不是测试的堆砌，而是对规则的定义。重构后跑测试，三组数据全绿。

本课核心 一条测试钉不住实现，第二条不同输入的测试才能。红灯时心里没底，就 Fake It 先绿，再用下一个例子三角定位；心里有底，就直接显然实现。到绿的三种姿势都合法，谎言的唯一死期是下一条测试。

检查一下手感

课后作业：三圈逆运算

现在造 Parse 的逆操作 ToHexString——正好把三角定位走全：

  1. 第 1 圈：ToHexString(new byte[] { 0x10 }) 应得 "10"。允许 Fake It：return "10";，亲眼看到绿。
  2. 第 2 圈：ToHexString(new byte[] { 0x7F }) 应得 "7F"。谎言崩塌，逼出 b.ToString("X2")（注意大写 X：小写 x2 会给你 7f）。
  3. 第 3 圈：ToHexString(new byte[] { 0x10, 0x02 }) 应得 "10 02"——逼出空格分隔。完成后把三条 [Fact] 收编成一条 [Theory]。
  4. 彩蛋：加一条 Theory 验证往返一致性——对任意帧，Parse(ToHexString(frame)) 等于原帧。这条在以后讲「不变式测试」时会重逢。
  5. 想一想（带回讨论）：作业里如果 Parse("") 直接写 return Array.Empty<byte>(); 就能绿——这算 Fake It，还是真实现？「假实现」在什么条件下可以直接转正？

本课首选原著：Kent Beck《Test-Driven Development: By Example》第 3 章——Money 例子正是用三角定位从「美元相等」走向「任意货币相等」，和本课 Parse 的路径一模一样。图书页。
