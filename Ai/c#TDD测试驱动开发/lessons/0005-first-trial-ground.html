课程内练习到今天可以验收了。对着这份清单打个勾：红灯先行（第 1 课）、三角定位逼走硬编码（第 2 课）、隐藏依赖开接缝（第 3 课）、替身与交互断言（第 4 课）——XorChecksum、Parse、FrameSender、TrySend，这一路都是你自己在 TddLab 里长出来的代码。技能在手上，缺的只剩一件事：用在你自己的战场。这课就办两件事——教你怎么挑第一块真实试验田；给你一套回应「写测试太慢」的说辞，团队推广和面试都用得上。

选田三问

第一块田选错，TDD 会被冤枉。工作项目里扫一圈，用三个问题过筛：

选田三问 ① 是纯逻辑吗？——输入输出能在测试里构造出来（解析、计算、校验、协议、状态机）；UI 排版和硬件直读先排除。
② 是新代码，还是能先开缝？——新模块最顺；老代码按第 3 课的办法先找接缝、再动刀。
③ 这周它会被大改吗？——需求还没冻结的功能，安全网建了又拆，先等等。

你的领域里现成的候选：SECS 报文头解析、指令超时重发策略、报警条件判断、串口收发的粘包拆包——最后一个我们马上在课里实战一遍，你看看它有多适合。

毕业实战：串口粘包拆包

写串口的人都吃过这个亏：port.Read 返回的字节是任意分块的——发送端可能两帧连着发（粘包），一帧也可能被拆成两半到（半包），都没有任何提示。所以每个串口程序都需要一个「收字节、攒着、凑够一帧就吐出来」的模块。这就是标准的第一块试验田：纯逻辑、输入好造、真实痛点。三圈走完：

第 1 圈 · 一帧整的

[Fact]
public void Feed_with_exactly_one_frame_returns_one_frame()
{
    var cutter = new FrameCutter(frameLength: 2);

    var frames = cutter.Feed(new byte[] { 0x10, 0x02 });

    Assert.Equal(new byte[][] { new byte[] { 0x10, 0x02 } }, frames);
}

红灯 → 绿。到绿的姿势随便选——Fake It（return new[] { bytes };）也行，你觉得显然实现已经出来了直接写也行。这次假设走了 Fake It。

第 2 圈 · 两帧粘一起

[Fact]
public void Feed_with_two_stuck_frames_returns_both()
{
    var cutter = new FrameCutter(frameLength: 2);

    var frames = cutter.Feed(new byte[] { 0x10, 0x02, 0x7F, 0x00 });

    Assert.Equal(new byte[][] { new byte[] { 0x10, 0x02 }, new byte[] { 0x7F, 0x00 } }, frames);
}

假的 return new[] { bytes }; 立刻崩——三角定位第二次上演。逼出来的真实现：按帧长切片。

第 3 圈 · 半包，然后补齐

[Fact]
public void Feed_with_half_frame_keeps_it_until_rest_arrives()
{
    var cutter = new FrameCutter(frameLength: 2);

    Assert.Empty(cutter.Feed(new byte[] { 0x10 }));   // 半包：先别出声
    Assert.Equal(new byte[][] { new byte[] { 0x10, 0x02 } },
                 cutter.Feed(new byte[] { 0x02 }));   // 补齐：现在出帧
}

第 2 圈的实现只看当次输入、不记事，半包的前半截直接被它扔了——红。要过这关，模块必须有记忆：

public class FrameCutter
{
    private readonly int _frameLength;
    private readonly List<byte> _buffer = new();

    public FrameCutter(int frameLength) => _frameLength = frameLength;

    public byte[][] Feed(byte[] bytes)
    {
        _buffer.AddRange(bytes);                          // 来了就攒着
        var frames = new List<byte[]>();
        while (_buffer.Count >= _frameLength)             // 够一帧就吐一帧
        {
            frames.Add(_buffer.Take(_frameLength).ToArray());
            _buffer.RemoveRange(0, _frameLength);
        }
        return frames.ToArray();
    }
}

三圈结束，全绿。注意刚才发生了什么：粘包、半包这两个真实痛点，是测试一行一行逼着实现去处理的——手写这段代码时你八成会漏掉半包，然后在现场抓三天。这就是「减少 bug 返工」那半句承诺的兑现方式。也注意 buffer 状态的存在本身，就是一个没有被测试覆盖的隐患（谁的 buffer？要不要清？）——记下这个感觉，它以后会变成你对「隐藏状态」的嗅觉。

「写测试太慢」的 30 秒回答

可以直接背 「慢不慢看怎么算账。写测试的 20 分钟，买回来的是三样东西：调试时间——半包这种 bug 手动复现要挂串口线抓半天，测试一跑就现形；重构底气——改完 5 秒知道没改坏；设计——难写的测试当场报警，不用等联调。我按功能算总账，不按每小时敲多少行算。」

诚实的另一半（说出去更可信）：TDD 不是所有地方都快。试探性的一次性脚本、纯排版 UI、还在探索方向的 spike——这些场景先跑通再说，别教条。分得清什么时候用，别人才信你真用过。Fowler 对收益与代价的总结见 Uses and Drawbacks of TDD。

推广策略：先锋田，不下军令

你在《代码整洁之道》里读过童子军军规——推广 TDD 用的是同一个思路：自己的新代码先行，不动别人的规则。全组邮件强制执行、把覆盖率塞进 KPI，只会收获阳奉阴违和粗制滥造的测试。能示范三个月，比能宣讲三小时有用得多——你的 TddLab 和第一块试验田，就是全部弹药。

检查一下手感

课后作业：把第一圈带回战场

  1. 在工作项目里用选田三问筛出一小块纯逻辑（解析、校验、计算、状态机都行），把函数签名（或想造的类名）记下来。
  2. 给它写下第一个红灯：测试名用行为句式——输入什么_应当什么，比如 Parse_secs_header_returns_device_id。跑一遍，亲眼看它红。
  3. 把签名和这条测试贴回对话——我们一起走完第一圈，这就是你的毕业答辩。

本课首选文献：Martin Fowler《Uses and Drawbacks of TDD》——推广前把利弊原文读一遍，质疑来时你引的是 Fowler 而不是口水。原文 · Kent Beck 说 TDD 是「管理编程中的恐惧」：《TDD by Example》前言。

选田拿不准、第一个测试写不出来、或者工作项目有保密顾虑不方便贴——都回对话里说，可以换备选田。你的老师（Claude）在这里等你的毕业答辩。
