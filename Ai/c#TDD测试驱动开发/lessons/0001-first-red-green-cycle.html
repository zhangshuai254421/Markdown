C# TDD 课程 · 第 1 课

第一轮红绿循环用一条串口帧校验和，把 RED → GREEN → REFACTOR 跑进手指

你在《代码整洁之道》里读到过 TDD，也知道它的承诺：改代码不再靠胆量，因为身后永远跟着一张安全网。但「知道」和「会用」之间隔着一样东西——节奏。这一课只做一件事：带你完整跑通一轮循环，让节奏第一次发生在你的手指上。

先记住这个节奏

TDD 的全部动作只有一个，被无限重复（Fowler；Beck, 2002）：

RED 红灯
为下一个小行为写一条测试，亲眼看它失败
→
GREEN 绿灯
用最小的代码让这条测试通过
→
REFACTOR 重构
绿灯保护下清理代码，测试保持全绿

支撑节奏的是三条铁律（Clean Code 第 9 章）：没有失败测试不写生产代码；测试只写到「刚好失败」；生产代码只写到「刚好通过」。纪律、清单和命令都浓缩在 红绿重构速查卡 里，本轮循环里随时翻。

动手：五分钟搭好试验场

例子取自你的老朋友——串口通讯。设备帧末尾常带一个 XOR 校验字节（LRC），今天我们用 TDD 造它：输入帧 0x10, 0x02，校验和 0x10 ^ 0x02 = 0x12。找个空目录：

dotnet new sln -n TddLab
dotnet new classlib -o FrameCodec           # 被测代码
dotnet new xunit    -o FrameCodec.Tests     # 测试项目
dotnet sln add FrameCodec FrameCodec.Tests
dotnet add FrameCodec.Tests reference FrameCodec
dotnet test                                  # 模板自带 1 条示例测试，全绿

把模板生成的 Class1.cs、UnitTest1.cs 删掉。试验场干净了。

RED：先写一个会失败的测试

注意顺序——测试在前，被测类根本还不存在。建 FrameCodec.Tests/ChecksumTests.cs：

using FrameCodec;
using Xunit;

public class ChecksumTests
{
    [Fact]
    public void Xor_of_10_and_02_is_12()
    {
        byte[] frame = { 0x10, 0x02 };
        Assert.Equal(0x12, Frame.XorChecksum(frame));
    }
}

跑 dotnet test：编译错误——Frame 不存在。这是本轮的第一个红灯，而且失败原因正确：那个功能确实还不存在（铁律二说编译错误也算失败）。

为了让红灯变成「断言级」的——更清晰、更接近以后每天看到的样子——建一个故意的空实现：

namespace FrameCodec;

public static class Frame
{
    public static byte XorChecksum(byte[] bytes)
    {
        return 0;   // 故意错的：只为让红灯有形
    }
}

再跑一次：Expected: 0x12 But was: 0x00。停三秒，看着这条红。你马上会明白为什么它是仪式。

GREEN：最小实现

目标只有一个：让这条测试通过。不多不少：

public static byte XorChecksum(byte[] bytes)
{
    byte acc = 0;
    foreach (var b in bytes) acc ^= b;
    return acc;
}

dotnet test —— 绿。克制住「顺手把 hex 解析、帧头校验都写了」的冲动：它们各自有属于自己的红灯，会在以后的循环里逼出来。

REFACTOR：绿灯保护下的清理

现在安全网张开了。做一轮小清理——重命名参数、换成表达力更好的写法：

public static byte XorChecksum(byte[] payload) =>
    payload.Aggregate((byte)0, (acc, b) => (byte)(acc ^ b));

再跑 dotnet test：依然绿。这就是你要的那张安全网——重构前不敢做的改动，现在做完一秒内就知道没改坏。体验过这一次，「重构更有底气」就不再是口号。

本课核心 先亲眼看它失败。一条从没红过的测试不可信：它可能因为默认值、环境或根本没被执行而「永远绿」。先红后绿，证明这条测试真的在检查你写的东西——这是 TDD 区别于「事后补测试」的第一道分水岭。

检查一下节奏感

课后作业：自己再跑三圈

在课堂代码上继续，每圈都严格走 红 → 绿 → 重构，每圈先亲眼看红：

  1. 全新行为：解析十六进制帧字符串——Frame.Parse("10 02") 应返回 new byte[] { 0x10, 0x02 }。建议拆小：Parse("10") 先红，绿了之后 Parse("10 02") 再红。
  2. 边界：Parse("") 应返回空数组。
  3. 想一想（不用写代码）：给已完成的 XorChecksum 补一条 XorChecksum(Array.Empty<byte>()) == 0x00 的测试。先预测：它是红是绿？跑了之后，这个结果和「先亲眼看它失败」矛盾吗？把你的想法带回来。

本课首选原著：Kent Beck《Test-Driven Development: By Example》第 1–2 章——Money 例子就是本课节奏的原型，读时会不断认出今天跑过的每一拍。图书页。

卡在哪一步、红灯颜色不对、作业里的「想一想」有疑问——随时回到对话里问你的老师（Claude），这就是答疑通道。下一课预告：Triangulation（三角定位）——怎么用第二条测试逼走硬编码，顺便认识 xUnit 的 Theory。
