C# TDD 课程 · 第 4 课

替身进阶：stub 与 mock手写假货的天花板，以及什么时候该断言「交互」而不是「状态」

先给你已经写过的东西发个学位证：第 3 课里的 RecordingChannel，学名叫 spy（间谍）——一个假装是依赖、暗地里记录调用供你事后检查的替身。也就是说，你已经在用测试替身了，只是没用这个名字。这一课做三件事：把替身的术语地图摆清楚（速查卡在这）；教你一种全新断言路线——交互断言；然后请出 mock 框架，看看它到底帮你省了什么。

先疼一次：重发需求

真实的工业现场从不一次成功：通道忙、干扰、半包。新需求很自然——通道忙就重试一次。按 TDD 的规矩，测试先行。这次替身需要新本事：先扔一次异常、再恢复正常，同时记住被调了几次：

public class ChannelBusyException : Exception { }

[Fact]
public void Send_retries_once_when_channel_is_busy()
{
    var channel = new FlakyChannel(failuresBeforeSuccess: 1);
    var sender  = new FrameSender(channel);

    sender.Send(new byte[] { 0x10, 0x02 });

    Assert.Equal(2, channel.Attempts);   // ← 注意这条：断言的不是数据，是「次数」
}

private class FlakyChannel : IFrameChannel
{
    private int _failuresLeft;
    public int Attempts { get; private set; }
    public byte[] LastWritten { get; private set; } = Array.Empty<byte>();

    public FlakyChannel(int failuresBeforeSuccess) => _failuresLeft = failuresBeforeSuccess;

    public void Write(byte[] bytes)
    {
        Attempts++;
        if (_failuresLeft-- > 0) throw new ChannelBusyException();
        LastWritten = bytes;
    }
}

红灯。让它变绿的实现也顺理成章：

public void Send(byte[] frame)
{
    var payload = frame.Append(Frame.XorChecksum(frame)).ToArray();
    try   { _channel.Write(payload); }
    catch (ChannelBusyException) { _channel.Write(payload); }
}

绿。但停下来看看 Assert.Equal(2, channel.Attempts)——它和你以前写的断言不是一路货：

你以前写的（状态断言）这条（交互断言）
问的问题「写出去的字节对吗」「跟依赖协作的方式对吗」
查的东西产出/落点的数据调用了几次、传了什么、调没调
适用绝大多数行为，默认选它没有状态可查时：重试、该调没调、不该调却调了

Send 返回 void、效果全在副作用里，「重试了几次」这个问题没有状态可查——只能去问依赖本人。这就是交互断言存在的理由。Martin Fowler 把这两条路线的分野写得很透：Mocks Aren't Stubs。

手写替身的天花板

刚才你一口气造了两个替身：FlakyChannel 的扔异常部分是 stub（替你安排依赖的「进」——返回值和异常），Attempts 计数部分是 spy（替你记录「出」）。加上 RecordingChannel，手写替身你已经玩得很熟了。那框架还能帮什么？看看同样的测试用 NSubstitute 写一遍：

using NSubstitute;

[Fact]
public void Send_retries_once_nsubstitute()
{
    var channel = Substitute.For<IFrameChannel>();     // 替身本体：IFrameChannel 的运行时实现
    var calls = 0;
    channel.When(c => c.Write(Arg.Any<byte[]>()))      // stub：安排「第一次扔异常」
           .Do(_ => { if (++calls == 1) throw new ChannelBusyException(); });

    new FrameSender(channel).Send(new byte[] { 0x10, 0x02 });

    channel.Received(2).Write(Arg.Any<byte[]>());      // mock：恰好被调 2 次，不多不少
}

对比一下你省掉了什么：再也不用为每个接口手写一个替身类。以前每换一个接口就要现编一个 RecordingXxx、FlakyXxx；现在 Substitute.For<接口>() 一行出一个万能替身，stub 用 Returns/When-Do 配置，spy 和 mock 合并成 Received() 一句话。替身多了之后，这笔账很可观。课程统一选 NSubstitute——语法最贴人话，也是 .NET 社区当下的主流选择（Moq 也常见，看得懂即可）。

再认识一句很可能成为你主力武器的断言——「绝不该发生」：

channel.DidNotReceive().Write(Arg.Any<byte[]>());   // 从未被调用，不管参数是什么

mock 的纪律：它是一面危险的镜子

警告 交互断言有一个成瘾性陷阱：它太好用了，好用到你忍不住把每一步协作都 Received() 一遍。一旦如此，测试就不再是「查行为的网」，而变成实现细节的镜子——你改的只是实现方式（行为没变），测试却红成一片。Fowler 对此的警告是 mock 派与经典派之争的核心，记住纪律：交互断言只留给「没有状态可查」的行为；重构之后莫名红灯，就是镜子照进现实的信号。
  • 默认状态断言，交互断言按需使用
  • 只 mock 出了边界的依赖（串口、邮件、数据库）；自己写的纯逻辑不 mock
  • 替身接口要窄——方法越少，替身越便宜

现在就做：给重发逻辑收尾

顺着刚才的故事走，一共三步，十分钟后你的 FrameSender 就是个能上战场的模样：

  1. 把 FlakyChannel 和重发测试抄进 TddLab，跑绿。这就是本课的练习——跟着上面的代码块做即可。
  2. dotnet add package NSubstitute（加在 FrameCodec.Tests 项目上），用 Received(2) 重写同一条测试，两种拍法都留着，跑一遍。
  3. 给 FrameSender 加一个 TrySend：通道连续两次忙就放弃并返回 false。用 When-Do 让替身永远忙，断言 Assert.False(ok) 加 Received(2)——「试了两次，不多不少」。
