# Mission: C# TDD（测试驱动开发）

## Why
8 年 C# 老兵，读《代码整洁之道》时知道了 TDD，但从未在项目里真正用过——测试都是事后补、时有时无，改代码全靠胆量和肉眼验证。想把「红绿重构」通过系统练习变成肌肉记忆：让重构有一张真实的安全网，让缺陷在写代码当下就暴露，让接口在测试的压力下自然长清晰，最终能把 TDD 带进团队、面试时也拿得出手。

## Success looks like
- 能不假思索地完成一轮「红 → 绿 → 重构」循环，并说清每步纪律：为什么先亲眼看红灯、为什么只写最小实现、为什么绿灯之后先重构再进下一轮
- 在课程练习里独立完成 10+ 轮循环后，能在工作项目的新功能上用 TDD 起步
- 能回应团队推广时的经典质疑：「写测试太慢」「测试是 QA 的事」「需求一变测试全废」
- xUnit 成为主力框架：Fact / Theory / InlineData 熟练，`dotnet test` 成为日常动作

## Constraints
- 8 年 C# 经验，语言、VS、dotnet CLI 都熟，不需要任何语言入门内容
- 写过测试但不系统：跳过「什么是单元测试」扫盲，重心在「先写测试」的节奏与纪律
- 框架定为 xUnit（用户选定）
- 课程内练习为主，熟练后再上工作项目；不过早推真实项目
- 领域背景：工业硬件（串口、激光器、SECS 协议）、WPF——练习示例尽量取自这些场景

## Out of scope
- WPF UI 自动化测试、性能/压力测试——先把纯逻辑层的 TDD 练扎实
- 其他语言生态（Java/JS/Python）的测试工具链
- CI/CD 集成——等循环跑顺之后再谈
