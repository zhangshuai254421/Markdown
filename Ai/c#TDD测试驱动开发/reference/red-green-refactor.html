Reference · 速查卡

RED · GREEN · REFACTORTDD 核心循环：纪律、清单与命令 —— 每一轮都回到这张卡

整个 TDD 只有一个动作，被无限重复：红 → 绿 → 重构。Kent Beck 在《Test-Driven Development: By Example》里把它定义为 TDD 的全部节奏（Beck, 2002）；Martin Fowler 把它压缩成一句「先写一个失败的测试，再让它通过，然后移除一切重复」（Fowler, TestDrivenDefinition）。

RED 红灯
为下一个小行为写一条测试，亲眼看它失败
→
GREEN 绿灯
用最小的代码让这条测试通过
→
REFACTOR 重构
绿灯保护下清理代码，测试保持全绿

三条铁律（Clean Code 第 9 章）

Robert C. Martin 在你读过的《代码整洁之道》第 9 章给出了 TDD 的三条铁律，一分钟就能背下来：

  1. 不在没有失败测试的情况下写生产代码——除非是为了让一个正在失败的测试通过。
  2. 不写比「刚好失败」更多的测试——编译错误也算失败。
  3. 不写比「刚好通过」更多的生产代码——多一行都不行。

每步纪律清单

RED 红灯

  • 只为一个行为写一条测试——这个行为还不存在
  • 跑一次，亲眼看它失败（dotnet test 或测试资源管理器）
  • 确认失败原因正确：断言失败，或因类型/方法不存在而编译失败
  • 红灯原因是「环境坏了」「别的测试连坐」= 无效红灯，先修环境

GREEN 绿灯

  • 目标只有一个：让当前这条红灯变绿
  • 写最小实现——硬编码返回值也行（Fake It），下一轮再泛化
  • 克制住「顺手把整个功能写完」的冲动
  • 跑测试，全绿，进入下一步

REFACTOR 重构

  • 只在全绿时动手重构——绿灯是重构的安全网
  • 一次只做一类小改动：重命名、提取方法、消除重复、移动代码
  • 每改一小步就跑一次测试；红回去了就撤销，退回绿灯再试
  • 不新增行为——新行为要回到 RED，开新一轮循环

CLI 速查

# 一次性搭好「实现 + 测试」双项目
dotnet new sln -n TddLab
dotnet new classlib -o FrameCodec           # 被测代码
dotnet new xunit    -o FrameCodec.Tests     # 测试项目（自带 xunit 包）
dotnet sln add FrameCodec FrameCodec.Tests
dotnet add FrameCodec.Tests reference FrameCodec

# 每轮红绿循环里反复执行
dotnet test                                 # 跑全部测试，看红/绿

# 可选：保存即重跑，红灯绿灯反馈更快
dotnet watch test

xUnit 速查

元素用途
[Fact]无参测试方法——一条测试说一件事
[Theory] + [InlineData(...)]同一逻辑、多组输入的参数化测试（第 2 课展开）
Assert.Equal(expected, actual)注意顺序：先期望值，后实际值
Assert.Throws<T>(() => ...)断言某个操作抛出指定异常
测试类 publicxUnit 为每条测试方法新建一个类实例——测试之间不共享状态

小术语表（持续扩充）

术语含义
红灯 / RED刚写的测试正在失败——这是好状态，是下一动作的起点
绿灯 / GREEN全部测试通过——可以安全重构或开下一轮
断言 / assertion测试里的「期望 vs 实际」检查；断言失败是最有效的红灯
最小实现恰好让当前测试通过的代码，多一行都不写
Fake It绿灯阶段用硬编码/假实现先让测试通过，之后再泛化
三角定位 / Triangulation用第二条测试逼出真实现而非硬编码（后续课程展开）
