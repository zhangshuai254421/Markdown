第一轮：从红灯到绿（最小实现）

第 7 课那条测试在逼出一个事实：引擎得记得每个位号的越限累计。最小实现——注意它有多克制：没有死区、没有恢复、没有搁置，那些各自有自己的红灯：

public sealed class AlarmEngine
{
    private readonly IAlarmDefinitionStore _store;
    private readonly IAlarmClock _clock;
    private readonly Dictionary<string, TagRuntime> _runtime = new();

    public event Action<AlarmEvent>? EventRaised;

    public AlarmEngine(IAlarmDefinitionStore store, IAlarmClock clock)
        { _store = store; _clock = clock; }

    public void OnCondition(ConditionChanged c)
    {
        var def = _store.Find(c.Tag);
        if (def is null) return;                    // 无档案，不报警——设计决策①
        var rt = _runtimeFor(def);

        if (rt.State != AlarmState.Normal) return;  // 已在报警中：不重复播报——设计决策②

        if (c.Value > def.Limit)
        {
            rt.OverAccum += c.At - rt.LastAt;       // 用条件自带的时间戳累计
            if (rt.OverAccum >= def.OnDelay)
            {
                rt.State = AlarmState.Unacknowledged;
                rt.RaisedAt = c.At;
                EventRaised?.Invoke(new AlarmRaised(def.Tag, c.At, def.Priority));
            }
        }
        else rt.OverAccum = TimeSpan.Zero;          // 回到限内：累计清零

        rt.LastAt = c.At;
    }
}
两个沉默的设计决策 ① 无档案不报警：采集层报来的条件若没有 MADB 档案，直接忽略——「先立档案再报警」，倒逼每条报警有出生证。② 报警中不重复播报：通讯层每秒都在报值，状态机保证 Raised 只发一次。这两条都是测试逼出来再定型的契约，不是顺手写的。

第二轮：确认、恢复与那格易错点

第 3 课那格「最容易做错的」现在要用测试钉死——两条路径分开测（老纪律）：

[Fact]
public void 已确认后条件恢复_产Closed_不出AutoReturned()
{
    var engine = EngineWithAlarm(out var clock);          // 触发 + 确认，处于 Acknowledged
    engine.OnCondition(new ConditionChanged(Tag, 247, clock.At(10 Min)));
    var last = events.Single(e => e is AlarmClosed);      // 有主人，直接闭环
    Assert.DoesNotContain(events, e => e is AlarmAutoReturned);
}

[Fact]
public void 未确认时条件恢复_产AutoReturned_且仍留活跃列表()
{
    var engine = EngineWithAlarm(out var clock);          // 只触发，无人确认
    engine.OnCondition(new ConditionChanged(Tag, 247, clock.At(10 Min)));
    Assert.Contains(events, e => e is AlarmAutoReturned); // RTN：没人看见的恢复要留影
    Assert.Single(engine.Active);                          // 还在列表里，闪绿等确认
}

绿灯的实现只需要一次状态判断：Acknowledged 恢复 → Closed + 移出列表；Unacknowledged 恢复 → AutoReturned + 状态转 RTN（列表里留着）。先看两条测试红，再让它们绿——顺序不能倒。

第三轮：活跃列表——引擎的读模型

UI 要的不是一个事件流，而是一个「现在什么挂着」的查询。给引擎加一个只读投影：

public IReadOnlyList<ActiveAlarm> Active { get; }
public record ActiveAlarm(string Tag, AlarmState State, Priority Priority, DateTimeOffset Since);

测试写四拍：触发 → 列表 1 条（Unacknowledged）；确认 → State 变 Acknowledged；已确认后恢复 → 列表 0 条；未确认恢复 → 列表仍是 1 条（RTN）。列表是事件流的投影，不是第二份真相——同一份数据的两个视图，永远不会对不上账（回想第 1 课：报警历史就是按位号筛出来的视图，同一哲学）。

搁置正门：引擎不撒谎，表现层按标过滤

第 3 课的三条搁置规矩——到期自动恢复、搁置清单单独可见、动作全量留痕——落到引擎里只有一句话的设计：

本课核心：搁置不是拦状态机，是给事件打标 搁置期间条件照常触发、状态照常流转、事件照常落历史——只是 AlarmRaised 上带着 ShelvedUntil 标。引擎不撒谎（全量记录），UI 按标过滤（主列表不显示），搁置清单 = Active.Where(ShelvedUntil > now)。到期不用定时器去「解除」——时钟一过，标自然失效。三条规矩一个机制全满足。

这个设计回答了一个容易想歪的方向：不要在引擎里做一个「搁置开关」去拦截状态机——那样历史库里就缺了搁置期间的记录，第 6 课的体检就成了瞎子。状态机的真相永远完整，呈现的裁量留给表现层。
