GB/T 41261 报警管理课程 · 第 3 课

报警状态机四状态五转换，和那个最常被省掉的 RTN ——「状态管理缺失」的主手术

先做个体检：在你现在的报警模块里，一条报警有几种状态？大概率是两种——「在列表里」和「不在列表里」。触发就进列表，恢复就消失，确认与否顶多改个颜色。这不是状态管理，这是名单管理。GB/T 41261-2022 给每条报警一台状态机：四个状态、五条合法转换——你的「记录混乱难追溯」，病根就在这台机器从来没被建过。

先分清：条件 vs 状态

混淆的总根源在这里。条件（condition）由工艺量决定：温度越没越限，采集层说了算。状态（state）由条件和人机交互共同决定：确认了没有、恢复确认了没有。温度回到限内 = 条件恢复了，但报警状态未必走完——还没人看见呢。把这两样塞进同一个 bool，就是你模块里「报警忽闪忽现、记录对不上账」的技术起点。

本课核心 条件看工艺，状态看交互。状态机管理的是「这条报警被人处理到哪一步了」——这是报警和普通日志行的本质区别。

四状态五转换

当前状态事件去向系统行为
Normal 正常条件越限未确认声光起，进报警列表，事件入库
未确认操作员确认已确认由闪变稳（闪红→稳红），责任接管
未确认条件恢复RTN 恢复未确认变闪绿，仍留列表等确认
已确认条件恢复Normal移出列表
RTN确认恢复Normal移出列表，闭环

颜色约定出自 ISA-18.1 惯例：未确认闪红、已确认稳红、恢复未确认闪绿（厂商实现的状态图对照；概念以国标正文为准，完整速查卡见 报警状态机速查卡）。

注意那格最容易做错的 RTN 只从「未确认」进入。标准的口径：RTN 是「条件在操作员确认之前就自己恢复了（auto-reset）」的状态。已确认的报警条件恢复后直接回 Normal——有主人的报警，回家不用再敲门。

RTN：最常被省掉的状态，最不能省的状态

设想半夜三点，某温度报警触发，凌晨两点自行恢复——注意，是先触发后恢复，全程没人开过界面。没有 RTN 的系统里，这条报警已经悄悄蒸发了；早班打开列表，一片祥和，昨夜发生过什么，列表不说，只能去翻流水账。这就是你「记录混乱难追溯」的经典现场。

RTN 的规矩是：条件在确认之前恢复，报警不消失，变闪绿留在列表里，等人补一个「看见了」。发生有人接管，恢复有人看见——环才闭上。凌晨那条温度报警，早班一打开就会看到它的 RTN：夜里出过事，自己好了，但你要知道。

补充一个进阶件：锁存（latch）——联锁、停机类报警常用，条件恢复也不灭，必须人工复位。它和 RTN 别混：RTN 等的是「确认看见」，锁存等的是「复位授权」。你的模块要不要锁存，写进《报警哲学》。

三种「合法闭嘴」：搁置、抑制、退出服务

报警烦人怎么办？标准给的答案不是「删」，而是三扇正门：

搁置 shelving运行态抑制 suppression退出服务 out-of-service
谁发起操作员（现场）组态逻辑（设计态）工程/维护
时限必须有，到期自动恢复（常以一个班次为上限）随设备状态自动生效/失效到检修结束
审批即时，但全量留痕走组态变更变更管理（MOC）
可见性主列表移除，搁置清单单独可见对操作员不可见（按设计）退出服务清单可见
典型场景吹扫期间某液位计乱报停机时不报「运行参数异常」检修仪表，相关报警长期退出

三扇门的共同意义：给合法的「闭嘴」留正门，堵死「删报警」这个后门。所有动作全量留痕。优先级（第 4 课）不改变这台状态机——它只是每条报警自带的属性。

练一把：当一次操作员

下面是真机。按这个剧本走一遍，盯住日志区——每个动作都落了一条带时刻的事件记录（第 1 课说的「报警的生命周期靠事件记录留痕」，这就是实物）：

  1. 点「条件越限」——看它闪红；再点一次？按钮灰了：Normal 时触发是唯一入口。
  2. 点「条件恢复」——注意它没有回家，变成闪绿的 RTN：没人看见过的报警，不许悄悄走。
  3. 点「确认恢复」——闭环，回 Normal。
  4. 再来一轮，这次先「操作员确认」再「条件恢复」——有主人的报警直接回家，不用二次确认。

课后作业：把状态机写进代码（TDD 回归）

TDD 课程毕业时说过，第一块试验田可以选「报警条件判断」——现在它来了，而且是纯逻辑，最适合先红后绿：

  1. 建模：AlarmState { Normal, Unacknowledged, Acknowledged, ReturnToNormal }；AlarmStateMachine 提供 Trigger() / Acknowledge() / Clear() / AcknowledgeReturn() 与 CurrentState。转换表就是上面那张五行的表。
  2. 先红：第一条测试定契约——new 出来是 Normal；Trigger() 之后是 Unacknowledged。亲眼看红再绿，节奏你熟。
  3. 设计决策题：非法转换（比如 Normal 时点 Acknowledge）抛 InvalidOperationException 还是静默忽略？先写测试定契约再决定——想想哪种对你的报警引擎调用方更友好。
  4. 边界分开测：Clear() 从 Acknowledged 进 Normal、从 Unacknowledged 进 RTN——两条路径的测试分开写。加分题：锁存要不要建模？想清楚再动手。
  5. 带回第一盏红灯（测试名或截图），毕业答辩传统。
