GB/T 41261 报警管理课程 · 第 4 课

合理化与优先级矩阵给每条报警办出生证：后果严重度 × 最大响应时间

第 1 课的三问是把刀，这一课把它升级成法庭。你从清单审计带回的那两个数字——总条数、非报警占比——就是送进法庭的卷宗。合理化（rationalization）就是逐条审判：够格的办出生证（进入主报警数据库），不够格的退回事件或提示。生命周期七阶段里它是公认最耗工的一格，但你的模块「定义随意」的病，只有这一副药。

每条候选的审判流程：三问过资格 → 不处理会怎样（后果）→ 操作员第一步干什么（操作动作）→ 有多少时间（MTR 最大响应时间）→ 查矩阵定优先级。铁律只有一条：优先级查矩阵，不凭嗓门——是「后果严重度和响应时间按哲学文档推出来的」，不是会上谁资历老听谁的。

优先级矩阵：怎么定级

分档先写在哲学文档里（每家不一样，下面是常用示例）：严重度三档——S1 人身安全/重大环境、S2 停产/设备损坏、S3 质量/产量/经济性；响应时间三档——T1 ≤5 分钟、T2 5–30 分钟、T3 >30 分钟。交叉出矩阵：

示例矩阵T1（≤5 分钟）T2（5–30 分钟）T3（>30 分钟）
S1 人身安全/重大环境高高中
S2 停产/设备损坏高中低
S3 质量/产量/经济性中低低

读法示范：加热板超温、不处理一炉报废（S2），必须 5 分钟内停炉（T1）→ 高。烘箱温度偏差只影响本批质量（S3），下班前处理就行（T3）→ 低。注意 S1 那一行——安全后果几乎「一路高」，只在响应窗很宽时降为中。

为什么卡配比 高优先级超过一成，「狼来了」就常态化了——高报警满天飞时，真正的高报警和普通报警在操作员眼里没有区别。配比是合理化质量的体检指标：评审完统计一下，偏差太大就回炉。

看「操作动作」那一行——第 1 课第三问（操作员知道该干什么吗）在档案里的落点。凡是填不出操作动作的候选，当庭退回：要么不是报警，要么先把指引补上。

落到你的模块：档案驱动，不再 if 里长报警

你现在的报警大概率长在代码里：if (temp > 250) 报警("温度过高")。按标准，这段逻辑要倒过来——引擎读档案，档案来自评审会：

public sealed record AlarmDefinition(
    string Tag,                // HEAT01_TEMP_HI —— 全系统唯一
    string Description,        // 加热板温度高于工艺上限
    AlarmClass Class,          // 安全 / 设备 / 工艺
    string Cause,              // 加热管失控或热电偶漂移
    string Consequence,        // 本炉产品全部报废
    string OperatorAction,     // 停炉切手动，通知工艺员
    TimeSpan MaxResponseTime,  // 5 分钟
    Severity Severity,         // S1/S2/S3 —— 矩阵的输入
    Priority Priority,         // 高/中/低 —— 矩阵的输出
    string Group,              // 车间/工段分组
    string RationalizedBy, string RationalizedOn);  // 评审留痕

这张 record 就是 MADB 在代码里的投影——数据存 JSON / SQLite / Excel 导入都行。新项目上线 = 建档案 + 引擎加载，不再是每个项目「看情况定义」。这就是你使命里「可复用框架」的第二块基石（第一块是《报警哲学》）。

练一把：坐上评审席

课后作业：开一场迷你评审会

  1. 写实哲学第 3 节：定你项目的严重度分档（S1/S2/S3 各举两个例子）和响应时间分档（T1/T2/T3 的分钟数），画出你的矩阵——示例分档别照抄，按你们工艺的真实后果定。
  2. 填五份档案：从你的真实报警清单里挑 5 条，逐条填 MADB 字段模板（填不出的字段就是最好的问题——带回对话）。
  3. 回收两笔账：清单审计的两个数字（总条数 / 非报警占比）；「谁是报警负责人」——迷你评审会的与会名单，现在该有答案了。

本课首选原文：GB/T 41261-2022《过程工业报警系统管理》「合理化」与「优先级」部分（购买正文后精读）。免费导读：Rockwell 合理化白皮书（MADB 怎么当「法定产出」管理）、MeroBix 合理化工作表（评审记录模板）。
