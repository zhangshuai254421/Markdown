GB/T 41261 报警管理课程 · 第 6 课

KPI 与性能监测给报警系统建体检中心——七项指标，一个数据源

前五课我们造了一台机器：判据（第 1 课）、生命周期与哲学（第 2 课）、状态机（第 3 课）、档案（第 4 课）、参数（第 5 课）。然后呢？第 2 课说过：报警会老化——工艺在变，设备在变，报警不会自己跟着变。没有体检，半年后一切打回原形，回到「看情况定义 2.0」。这就是生命周期外围那件贯穿全程的事：监测与评估。好消息是，全部指标只有一个数据源——你第 1 课就建好的那个「本子」：事件历史库。

七项体检指标

指标定义与算法目标
平均报警率报警总数 ÷ 小时（每操作员口径）≤6 条/时（≈1 条/10 分，≈150 条/天）
峰值（10 分钟桶）任一 10 分钟桶内的最大报警数≤5 条；10 条是可管理上限
泛滥 flood10 分钟 >10 条即入泛滥；统计泛滥时间占比占比 <1%
优先级配比高/中/低各级占比~5% / ~15% / ~80%
颤抖 chattering同一来源 60 秒内 ≥3 次转换此类报警 0 台
驻留 standing活跃持续 >1 小时0 条（现实 <5）
陈旧 stale活跃持续 >24 小时0 条（现实 <5）

目标值是 EEMUA 191 基准（ISA-18.2 监测指标与其一致），行业经验值而非法定值——写进你家《报警哲学》时可按现实调整，但要有意为之。逐项出处与「超标后查什么」见 KPI 目标表速查卡。

本课核心 七项指标全部从事件历史库算出来——第 1 课那句「报警的生命周期靠事件记录留痕」在这里收利息：留痕是复利，体检是提现。没有结构化的事件记录，这七项一个都算不出来——这正是很多老系统「想管也无从管起」的原因。

怎么算：全是历史库上的聚合

对 C# 程序员来说，体检中心就是一组 LINQ 聚合。两个代表：

// ① 10 分钟桶：峰值与泛滥的基础
var buckets =
    from r in history                                  // 事件历史库
    group r by (int)(r.Timestamp.Ticks / TimeSpan.FromMinutes(10).Ticks) into g
    select new { Bucket = g.Key, Count = g.Count() };

int peak        = buckets.Max(b => b.Count);
int floodBuckets = buckets.Count(b => b.Count > 10);
double floodPct = 100.0 * floodBuckets * 10 / totalMinutes;

// ② 颤抖检测：同一来源的滑动 60 秒转换窗口
// 按位号分组 → 时间排序 → 滑窗计数 ≥3 即上榜
var chatteringTags = DetectChattering(history, window: TimeSpan.FromSeconds(60), threshold: 3);

注意体检的对象是报警，不是事件——所以进聚合前先按类别过滤：这就是第 1 课三问分类在数据层的直接回报。混进去一批「启机记录」，平均率直接失真。

体检的节奏：三个频率

频率动作谁
每班看板 1 分钟：昨日总数、当前泛滥/驻留数操作员 / 班长
每周Top-10 最响仪器排行 + 颤抖清单跟踪归零报警负责人
每年全量 KPI 评审 → 修订《报警哲学》→ 触发回炉评审会

周会的 Top-10 排行几乎是白捡的收益：行业经验里，最响的少数几台仪器常年贡献大头的报警记录——修好它们，报表立刻好看。第 5 课作业让你翻的「最烦的那台」，就是这份排行榜的 1 号展品。年度评审则是生命周期闭环的最后一口：体检结果回灌哲学，环就转起来了（第 2 课的「环不是清单」在这里落地）。

体检室：把你的数字放进来

检查一下体检知识

课后作业：给自家系统做第一次体检

  1. 导数：从你现有系统导出最近 24 小时的报警记录（能导 CSV 最好；只能人工统计就数：总数、最差 10 分钟、活跃超 1 时的条数）。
  2. 体检：填进上面的记分卡，把「达标 N / 7」带回对话。第 1 课你统计过「非报警占比」——对照一下平均报警率超标多少，两个数字互相印证。
  3. 诊断 Top-3：最响的三台仪器，各给一句诊断（颤抖？驻留？泛滥源？）——它们就是第 7 课改造方案的三个首发病例。
