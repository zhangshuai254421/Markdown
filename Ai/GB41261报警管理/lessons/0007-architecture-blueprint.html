GB/T 41261 报警管理课程 · 第 7 课

模块改造总装六课知识住进三个组件层——C# 落地系列开课

从这课起，课程换了性质：前六课是「学标准」，现在是「改模块」。先说清你现有模块的真问题——不是代码烂，是概念没分家：报警、事件、日志一锅炖（第 1 课），状态散落在几个 bool 里（第 3 课），参数写死在 if 里（第 4 课）。改造不是重写，是按标准把概念分家——概念分清楚了，组件边界自然就出来了。这张蓝图就是六课知识的落户图。

三层 + 三横切

出口/表现层 —— 声光、报警列表、弹窗（WPF）
消费 AlarmEvent 流 + 查询活跃列表。按优先级呈现（闪红/稳红/闪绿），搁置清单单独可见。自己不做任何判定。
↑ 订阅事件 / 查询　　↓ 条件事实
报警引擎层 —— 全系统唯一「懂报警」的地方
读档案 → 死区/延时滤波 → 四状态机 → 产出 AlarmEvent 流与活跃列表。纯逻辑、无 UI 依赖、全程可 TDD。
↑ ConditionChanged（条件事实）
采集/条件层 —— 设备通讯、数值比较
只产出「条件事实」：某点此刻的值。不懂得「报警」二字——是不是报警、几级、怎么呈现，一层都不许管。
······横切（三层都落）······
横切：事件历史库 · 性能统计 · 哲学配置
历史库 append-only（引擎产出全量落库）；性能统计 = 历史库上的只读聚合（KPI）；哲学配置 = AlarmDefinition 的存储（JSON / SQLite）。
本课核心一：分层就是把三句老话写成边界 「报警要人做事，事件陈述发生，日志负责记本子」（第 1 课）= 引擎层 / 事件流 / 历史库三条线。判定权只许住在引擎层——表现层只呈现、采集层只报事实，谁越界谁就是在再造「看情况定义」。

一条报警在数据上的样子——事件就是它的履历：

public abstract record AlarmEvent(string Tag, DateTimeOffset At);
public record AlarmRaised(string Tag, DateTimeOffset At, Priority Priority) : AlarmEvent(Tag, At);
public record AlarmAcknowledged(string Tag, DateTimeOffset At, string Operator) : AlarmEvent(Tag, At);
public record AlarmAutoReturned(string Tag, DateTimeOffset At)      : AlarmEvent(Tag, At); // 无人看见 → RTN
public record AlarmClosed(string Tag, DateTimeOffset At)            : AlarmEvent(Tag, At); // 闭环

AlarmAutoReturned 与 AlarmClosed 的区分，就是第 3 课那格易错点在数据上的化身：没被看见的恢复（RTN）和真正的闭环，必须记成两种事件——早班的「昨夜发生过什么」就靠这条区别。

接缝：TDD 老朋友的三次回归

引擎要可测，三个依赖必须做成接口——每个都是《TDD》课讲过的接缝（seam）：

public interface IConditionSource;          // 条件从哪来 → 测试里直接喂序列
public interface IAlarmClock { DateTimeOffset Now { get; } }  // 延时/驻留都要看表 → 拨表测试
public interface IAlarmDefinitionStore;     // 档案从哪来 → 测试用内存档案
本课核心二：IAlarmClock 是延时的救命缝 「越限持续满 2 秒才报警」这种逻辑，直接 DateTime.Now 就没法测——你总不能让测试睡 2 秒。注入时钟后，FakeClock 想拨到几点拨到几点。凡是依赖时间的逻辑，时钟必须走接缝。这是第 4 课（TDD）测试替身最实用的一次落地。

数据流走查：一条报警的代码一生

拍发生什么谁动的
1通讯层收到 ConditionChanged("HEAT01_TEMP", 265℃)采集层——只报事实
2引擎查档案 HEAT01_TEMP_HI（限值 250 / 死区 2 / 延时 2s / 高优先级）引擎 × 档案
3越限持续满 2 秒 → Raised（闪红起，进活跃列表）引擎（Evaluator + 状态机）
4Raised 落历史库 + 推给 UI横切 + 出口层
5操作员确认 → Acknowledged（稳红）→ 降温到 248 以下 → Closed全链路
6若没人确认温度就掉回 248 → AlarmAutoReturned（闪绿 RTN 留列表）引擎——第 3 课的规矩

第 6 拍就是「半夜报警清晨才有人看」那条场景的代码形态——状态机的每条规矩，最终都是一行数据流。

迁移路径：存量项目四步走

① 只建历史库
不动现有报警，零风险拿到 KPI 基线（第 6 课记分卡的数字从这来）
② 影子模式
档案+引擎并行运行：只写历史不接管 UI，新旧对比验证
③ 按工段切换
有档案的接管 UI，没档案的回炉评审——逐条退役，不一次性换血
④ 看板上线
KPI 进值班室，进入生命周期环的监测常态

第一步是整个迁移的支点：什么都不改，只开始记事件——一周后你就有了基线数字，改造的紧迫性和优先级自己浮出来。这也回答了「改造要不要停机大干一场」：不用，它是渐进的。

  2. 第一盏红灯（本课示范的测试，抄进 Tests 里）：
[Fact]
public void 越限持续满延时_产出Raised事件()
{
    var clock = new FakeClock();
    var engine = new AlarmEngine(StoreWith(HEAT01_TEMP_HI, onDelay: TimeSpan.FromSeconds(2)), clock);
    var events = new List<AlarmEvent>();
    engine.EventRaised += events.Add;

    engine.OnCondition(new ConditionChanged("HEAT01_TEMP", 251, clock.At(0)));
    Assert.Empty(events);          // 延时未满——寂静也是断言

    engine.OnCondition(new ConditionChanged("HEAT01_TEMP", 252, clock.At(TimeSpan.FromSeconds(2.1))));
    Assert.IsType<AlarmRaised>(events.Single());
}

这条红灯一红，它会把骨架里缺的每个零件逐个逼出来：档案存储、时钟接缝、延时判定、事件出口——让测试替你画架构图。

  1. 走完红 → 绿 → 重构；绿的时候回答一个问题带回：FakeClock 属于测试替身里的哪一种（dummy/stub/spy）？
  2. 回收零件：第 3 课的 AlarmStateMachine、第 5 课的 HysteresisEvaluator 做过的直接搬进 Core 当引擎内脏；没做的这课正好补——它们马上就要上岗了。
