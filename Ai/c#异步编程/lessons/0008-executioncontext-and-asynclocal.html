← 上一课：异步流

一个反直觉的问题

第 3 课说过：async 的续延可能跑在完全不同的线程池线程上。那问题来了——

提问 HttpContext、AsyncLocal<T> 这些「当前环境数据」，为什么 await 之后（线程都换了）还能读到正确的值？数据是怎么「跟过来」的？

同步时代：靠线程

以前没有 async 时，「环境数据」都是靠线程区分的：[ThreadStatic] 字段、ThreadLocal<T>。同一个线程内读写一致，换个线程就读不到了。

但 async 一来，这个方法可能「上半段在 A 线程、下半段在 B 线程」，只靠线程，数据就丢了：

[ThreadStatic] static string _threadValue;                  // 跟线程走
static AsyncLocal<string> _asyncValue = new();             // 跟逻辑上下文走

async Task DoWorkAsync()
{
    _threadValue = "hello";
    _asyncValue.Value = "hello";

    await Task.Delay(100);                     // 续延通常跑在别的线程池线程

    Console.WriteLine(_threadValue);           // 大概率 null（线程换了）
    Console.WriteLine(_asyncValue.Value);      // 稳定输出 "hello"
}

答案：ExecutionContext

ExecutionContext 是「逻辑上下文」的容器，装着环境数据（AsyncLocal 的值、安全信息等）。它的机制就两个动作：

  • 捕获（Capture）：async 方法 await 一个未完成的 Task 时，把当前 ExecutionContext 快照下来。
  • 恢复（Restore/Run）：续延被调度到别的线程时，先把这个 ExecutionContext 恢复，再执行续延。

所以续延虽然换了线程，但读到的环境数据还是原来那份。.NET 里几乎所有异步 API（Task.Run、ThreadPool.QueueUserWorkItem、await…）都会自动捕获并恢复 ExecutionContext。

AsyncLocal<T>：构建在它之上的环境变量

AsyncLocal<T> 就是「跨 await 流动的环境变量」：写入后，整个异步逻辑流里都能读到（含续延），且各异步流之间互相隔离。

谁在用？举几个你天天见的：

  • HttpContext / HttpContextAccessor（ASP.NET Core）：靠 AsyncLocal 存当前请求上下文。
  • Activity / 分布式追踪（OpenTelemetry）：把 trace id 带进异步流。
  • CultureInfo.CurrentCulture：当前语言区域，默认也会跨 await 保持。

一个关键误解：ConfigureAwait(false) 断不断它？

记住 ConfigureAwait(false) 只断开 SynchronizationContext（续延回不回原上下文），断不开 ExecutionContext。所以即使 ConfigureAwait(false)，AsyncLocal<T>、HttpContext 这些环境数据照样跟着走。

很多人以为 ConfigureAwait(false) 会「切断上下文、数据就没了」——这是两个不同的「上下文」被混淆了。一个是「调度回哪」，一个是「数据带不带」。

一个坑：Parallel.For 不自动流动

大部分高层 API（await、Task.Run）自动处理 ExecutionContext，但手动并行要小心——Parallel.For 不会自动捕获/恢复它，需要你手动包一层：

var ec = ExecutionContext.Capture();          // 手动捕获
Parallel.For(0, 30, _ =>
{
    ExecutionContext.Run(ec, _ =>            // 手动恢复
    {
        _asyncValue.Value = DoWork();
    }, null);
});

业务代码一般碰不到这个，但理解了「高层 API 自动帮你 Capture/Run」，你就知道为什么它无处不在却看不见。
