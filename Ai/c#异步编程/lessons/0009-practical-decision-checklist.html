决策 1：这个方法该同步还是异步？

先问本质：它是 I/O 密集 还是 CPU 密集？

  • I/O 密集（网络、文件、数据库、串口）→ 用真异步（HttpClient、FileStream.ReadAsync、真异步串口库）。
  • CPU 密集（计算、图像处理）→ 保持同步签名，让调用方决定要不要 Task.Run 卸载。
铁律 同步方法用同步签名，异步方法用异步签名。别做假异步：别把同步方法包成 await Task.Run(...) 藏在库内部。

决策 2：async void 能用吗？

只有事件处理器能用（签名固定 void，别无选择）。其余一律 async Task / async Task<T>。

原因：async void 异常没有 Task 可装，会直接炸到上下文；在 ASP.NET Core/控制台里直接崩进程。

决策 3：要不要 ConfigureAwait(false)？

  • 库代码：默认加 ConfigureAwait(false)（库不该依赖特定 UI/框架上下文）。
  • 应用代码（UI 控制器、ASP.NET Core）：通常不加（续延要回原上下文）。
别误用 ConfigureAwait(false) 不是躲死锁的工具——那是 hack。防死锁的正解永远是「别阻塞」。

决策 4：Task.Run 用在哪儿？

  • ✅ 只用于：CPU-bound 工作在「调用点」卸载（比如 UI 线程要算个重的，别卡 UI）。
  • ❌ 别用于：真正的 I/O（有真异步 API 就别包）。
  • ❌ 别藏在库方法内部（调用方失去选择权）。

决策 5：能不能阻塞？

有 SynchronizationContext 的线程（UI / 旧 ASP.NET）上，永远别 .Result / .Wait() / .GetAwaiter().GetResult()。坚持 async 一路到底（async all the way down）。

决策 6：Task 还是 ValueTask？

  • 默认 Task。
  • 只有热路径测量出分配压力，才换 ValueTask，并记住它的限制（不能 await 两次、不能并发等待）。

决策 7：要不要加取消？

长任务 / 可被用户取消的操作，接受 CancellationToken 并一路传下去：底层 API 传 token，自己写检查点 ThrowIfCancellationRequested()。默认 CancellationToken.None。

决策 8：异常怎么处理？

  • await 出错 Task → 在 await 处 try/catch，抓到的是原始异常（非 AggregateException）。
  • 别 fire-and-forget；真要，异常必须显式记日志或用后台任务承载。
