Task.Run 到底借不借线程

回到第一课埋下的区分。这里把它坐实：

关键 Task.Run(() => ...) 返回的是委托任务：它把委托排进线程池队列，等一个线程池线程来执行。它需要并占有一个真实线程。

所以 Task.Run 和「真异步 I/O」是两回事：

// CPU-bound：要算，用 Task.Run 把活丢给线程池（比如从 UI 线程卸载）
var result = await Task.Run(() => ComputeHeavy(input));

// I/O-bound：本来就是异步的，别再包 Task.Run
var html = await httpClient.GetStringAsync(url);   // 等待期间无线程

一句话记住：async/await 解决「等 I/O 时别占线程」；Task.Run 解决「要算时找个线程来算」。

线程池怎么调度

.NET 的线程池是一组复用的工作线程：

  • 有全局队列 + 每个线程一个本地队列；线程会从别的线程的本地队列「偷活」（work-stealing）来平衡负载。
  • 续延（async 唤醒）、Task.Run 的委托、ThreadPool.QueueUserWorkItem，都进这个池。

但最要命的一点是——

诊断要点 线程池会动态加线程，但注入很慢（大约每秒一个）。如果线程池线程都被阻塞在同步 I/O 上，它加线程的速度远远赶不上请求涌入的速度，吞吐就会崩。

这正是「别阻塞线程池线程」「async 一路到底」的底层原因：真正的异步 I/O 在等待时把线程还回池子，线程才能去服务别的请求。

Task.Run 的使用礼仪

Stephen Cleary 的规矩，照着做就不会错：

  • 别在库方法内部包 Task.Run 做「假异步」——把同步方法套一层 await Task.Run(...) 只是换了个线程阻塞，不是真异步。库方法要么保持同步签名，要么换成真异步实现。
  • Task.Run 属于「调用点」——比如 UI 线程要跑一段 CPU-bound 活，调用方决定包不包。
  • 先换真异步：WebClient → HttpClient、Thread.Sleep → Task.Delay。
  • ASP.NET 里 await Task.Run 是四重浪费：多余线程切换、额外 GC、扰乱线程池启发式、客户端断线时无法提前终止请求。服务端要么真异步 I/O，要么同步干。
// 反模式：把同步方法包成「假异步」藏在实现里
async Task<int> BadAsync()
{
    return await Task.Run(() => ComputeHeavy());   // 别这样
}

ValueTask：凭什么能省分配

Task 是类（引用类型），每次返回都要分配一个堆对象。运行时缓存了 Task.CompletedTask 和几个 Task<bool>/Task<int>，但很多「同步完成」仍会分配。

ValueTask<T> 是结构体：

  • 同步完成：直接把 TResult 包进去，零分配。
  • 异步完成：才包一个 Task<T>（.NET Core 2.1 起还能借 IValueTaskSource 池化，异步也零分配）。
// 高频路径：缓存命中时同步完成，零分配
ValueTask<int> GetAsync()
{
    if (cache.TryGet(key, out var value))
        return new ValueTask<int>(value);   // 零分配
    return new ValueTask<int>(FetchAndCacheAsync(key));
}
限制 ValueTask 不能被 await 两次、不能并发等待、不能在完成前 .GetAwaiter().GetResult() 阻塞。默认用 Task；只有测量到热路径的分配压力时，才换 ValueTask。
