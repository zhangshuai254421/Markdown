第二课的伏笔，现在拆开

还记得状态机的 try/catch 吗？async 方法里抛的异常，会被捕获、用 SetException 塞进返回的 Task。所以异常在 async 世界里是「存储-再抛出」的两段式，不是同步那样直接抛。

async Task DoWorkAsync()
{
    await Task.Delay(100);
    throw new InvalidOperationException("boom");   // 被塞进 Task
}

// 调用方：
try
{
    await DoWorkAsync();          // 异常在 await 处被重新抛出
}
catch (InvalidOperationException ex)   // 注意：是原始类型！
{
    // ...
}

两个关键事实：

  • await 会「解包」：直接抛第一个原始异常，不是 AggregateException。
  • .Result / .Wait() 抛 AggregateException：因为 Task 理论上可能聚合多个异常（如 Task.WhenAll）。

雷区一：fire-and-forget 静默吞异常

如果你调用一个 async Task 方法，却不 await 它：

_ = DoWorkAsync();   // 发起但不等待，异常无人拆包 → 静默丢失

异常被塞进了 Task，但没人去观察那个 Task，于是它永远不冒出来。你的程序照常跑，bug 却已经埋下了——这是最阴险的一类问题。

诊断要点 看到代码里「调用了返回 Task 的方法却没 await、也没赋给变量」或 _ = 丢弃，就要追问：它的异常打算怎么办？真要 fire-and-forget，必须显式把异常记进日志，或用后台任务（hosted service）承载。

雷区二：async void 能炸掉整个进程

async void 没有 Task 可装异常。那它的异常去哪了？直接抛到当前 SynchronizationContext：

  • 在 WPF/WinForms 里：抛到 UI 线程，成为未处理异常，可能崩界面。
  • 在 ASP.NET Core / 控制台里：没有上下文，直接抛到线程池线程，炸掉整个进程。

David Fowler 的原话：async void 在 ASP.NET Core 里永远是错的，绝不要用。

唯一例外 async void 只用于事件处理器（如 OnButtonClick），因为事件签名固定是 void，别无选择。其余一律 async Task / async Task<T>。

雷区三：取消不是「杀线程」

想中止一个长任务？正确工具是 CancellationToken，但它是协作式的——不是强制杀线程，而是「设一个标志，任务自己检查退出」。

using var cts = new CancellationTokenSource();
var token = cts.Token;

var task = DownloadAsync(url, token);
cts.Cancel();          // 触发取消（只是设置标志）

async Task<string> DownloadAsync(string url, CancellationToken token)
{
    using var resp = await http.GetAsync(url, token);   // ① token 传给底层 API
    token.ThrowIfCancellationRequested();               // ② 自己的检查点
    return await resp.Content.ReadAsStringAsync(token);
}
  • 取消发生时，通常抛 OperationCanceledException（TaskCanceledException 继承自它），Task 进入 Canceled 状态（不是 Faulted）。
  • 惯例：async 方法接受一个 CancellationToken 参数（默认 CancellationToken.None），并把它一路传下去。
