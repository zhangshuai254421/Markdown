Lesson 0002 · 编译器层

编译器把 async 方法变成了状态机 async 不是新线程，也不是新 Task——它是一段「分片执行、随时暂停」的机器。读懂它，你就看穿了 await 的全部魔法。

← 上一课：async 不是多线程

上一课的悬念

第一课说：await 是把「方法后半段」登记成续延。但编译器怎么做到把一个连续的方法切成两半，还能在将来从中间接着跑？

答案：编译器把你的方法改写成一台状态机。

先记住一个事实

关键 async 不是方法签名的一部分（就像 unsafe）。它不改变方法返回类型，只告诉编译器：把这个方法体按 await 切成若干段，编译成状态机。

你写的 vs 编译器生成的

这是你写的：

async Task<int> AddAsync(int a, int b)
{
    await Task.Delay(1);
    return a + b;
}

这是编译器改写的简化伪代码（真实生成代码更长，见文末主来源）：

struct AddAsyncStateMachine : IAsyncStateMachine
{
    int state = -1;                        // 记录「跑到哪一段了」
    AsyncTaskMethodBuilder<int> builder;  // 负责生成/完成 Task
    int a, b;                              // 参数和局部变量 → 变成字段
    TaskAwaiter awaiter;                   // 保存当前 await 的等待器

    void MoveNext()
    {
        try
        {
            if (state != 0)                    // 第一次进来
            {
                awaiter = Task.Delay(1).GetAwaiter();
                if (!awaiter.IsCompleted)      // 还没完成 → 要挂起
                {
                    state = 0;                 // 记下「下次从 await 之后继续」
                    builder.AwaitUnsafeOnCompleted(ref awaiter, ref this);
                    return;                    // ← 立刻返回，不阻塞！
                }
            }
            // 快路径，或续延被唤醒后，落到这里
            awaiter.GetResult();               // 取结果（出错则抛异常）
            builder.SetResult(a + b);          // Task 完成
        }
        catch (Exception ex)
        {
            builder.SetException(ex);          // 异常塞进 Task
        }
    }
}

这台机器怎么运转

抓住四个动作，整台机器就通了：

  • 挂起 = return。当 await 的 Task 还没完成，MoveNext 把 state 改成下一段，然后直接 return——这就是「不阻塞」在编译器层面的实现。
  • 续延 = 再调一次 MoveNext。Task 完成后，AwaitUnsafeOnCompleted 登记的回调会再次调用 MoveNext，它根据 state 跳到上次停下的地方接着跑。
  • 参数和局部变量 → 字段。因为方法「暂停」后栈帧就没了，所有要跨 await 存活的东西都得搬进结构体的字段里存着。
  • builder 管 Task 的一生。创建 Task、SetResult、SetException 都由 AsyncTaskMethodBuilder 完成。

两个分配上的真相

性能关键
  • 快路径零分配：如果所有 await 都同步完成（比如缓存命中、Task 已完成），状态机结构体根本不离开栈，不装箱、不堆分配。
  • 真正挂起才装箱：一旦异步挂起，结构体必须被装箱到堆上——因为栈会消失，而续延将来才运行。

这也是为什么 async 方法的开销「按需支付」：完全同步的 async 方法几乎没有分配成本。

顺带看清一件事：异常去哪了

注意伪代码里的 try/catch：async 方法里抛的异常，不会直接炸到调用方，而是被 SetException 塞进返回的 Task。等你 await 这个 Task 时，它才重新抛出。

这解释了后面会讲的两个现象：fire-and-forget 的异常会被吞（没 await 就没人拆包），以及 await 出错的 Task 会在 await 处抛异常。先埋个伏笔。
