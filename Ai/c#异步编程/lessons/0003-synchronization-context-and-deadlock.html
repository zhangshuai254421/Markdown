上一课的悬念

第二课说：Task 完成后，续延会被「某个线程」唤醒继续跑。那么到底是哪个线程？

答案由一个东西决定：SynchronizationContext。

SynchronizationContext 是什么

它是一个调度抽象，回答一个问题：await 之后的续延，该被「投递」（post）回哪个线程或上下文？

  • 默认（无上下文）：控制台程序、线程池。续延直接跑在线程池上。
  • UI 应用（WPF / WinForms）：上下文是「回到 UI 线程」——续延被 post 进 UI 的消息循环，由 UI 线程执行。因为只有 UI 线程能碰控件。
  • .NET Framework 的 ASP.NET：请求上下文，限定同一时间只有一个线程处理该请求。

ConfigureAwait 在改什么

await 默认等价于 ConfigureAwait(true)：续延尝试回到 await 前捕获的那个上下文。

// 默认：续延回到原上下文（如 UI 线程）
await SomeAsync();

// 显式：续延不用回原上下文，直接在线程池跑
await SomeAsync().ConfigureAwait(false);

区别只有一点：续延要不要「回家」。回到 UI 上下文更安全（能碰控件），但有开销；回线程池更快，但不能直接碰 UI。

死锁是怎么发生的

经典场景：WPF/WinForms 的 UI 线程（或 .NET Framework 的 ASP.NET）上，同步阻塞了一个异步方法。

// 运行在 UI 线程上
void OnButtonClick()
{
    string html = GetHtmlAsync().Result;   // ← 用 .Result 同步阻塞！
}

async Task<string> GetHtmlAsync()
{
    string html = await http.GetStringAsync(url);
    return html;
}

四步走进死锁：

  1. UI 线程调用 GetHtmlAsync()，执行到 await（网络 I/O 挂起），方法返回一个未完成的 Task。
  2. OnButtonClick 调 .Result，把 UI 线程卡住，原地等这个 Task 完成。
  3. 网络 I/O 完成，续延要回来——它默认要回到 UI 线程的 SynchronizationContext。
  4. 但 UI 线程正被 .Result 占着，续延永远排不上队。于是 .Result 等 Task，Task 的续延等 UI 线程空出来——互相等，死锁。
诊断要点 这不是「线程池被耗尽」，而是「上下文线程被阻塞，续延回不去」。看到 .Result / .Wait() / .GetAwaiter().GetResult() 出现在有上下文的线程上，就要警觉。

两条防线

Stephen Cleary 给的标准答案：

正解
  1. 别阻塞异步代码（async all the way down）：把 OnButtonClick 改成 async void，用 await 而不是 .Result。上下文始终没被阻塞，死锁从根上消失。
  2. 库代码用 ConfigureAwait(false)：让库的续延不回原上下文，这样无论谁在什么上下文调用它，都不会「需要」那个上下文。

但 Cleary 特别警告：

危险实践 用 ConfigureAwait(false) 去「躲」一个已知死锁是 hack。因为你必须覆盖整条调用链（含第三方库）里的每一个 await，这根本不可控。真正的解药永远是「别阻塞」。

现代 .NET 的一个重要变化

记住这条，能省你很多误判：

关键事实 ASP.NET Core 移除了 SynchronizationContext。所以在 ASP.NET Core 里，上面那个「.Result + 回请求上下文」的经典死锁基本不会发生。但 WPF / WinForms / WinUI 这些 UI 框架仍然有上下文，坑依然真实存在。

所以现在 ConfigureAwait(false) 在 ASP.NET Core 里主要是个「省一点点调度开销」的习惯，不再关乎死锁；但在 UI 应用里，它和「别阻塞」依然关键。
