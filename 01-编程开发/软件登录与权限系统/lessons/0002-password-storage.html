软件登录与权限系统 · 第 2 课（纯桌面版）

密码怎么存才不算裸奔哈希、盐、慢哈希三件套——本地库被拷走之后，密码列是你最后的防线

桌面软件的密码存在本地库里（SQLite / LocalDB / 中央 SQL Server），而本地库有个比服务器更常见的遭遇：被整份拷走——装机 Ghost、共享文件夹里的数据目录、用户顺手备份。所以第 1 课「诚实边界」之下，这一课的问题变得非常具体：库文件到了别人电脑上，你的密码列还守得住吗？守不住的存法，等于把所有用户的密码连同数据库一起送人。

三种常见答案，为什么都不合格

存法看似合理之处为什么不行
明文简单直接，还能「找回密码」库被拷走密码全泄露。所谓「找回密码」恰恰是暴露点——能还原原密码的存储，等于没设防
可逆加密（AES 等）「我加密了，很安全」加密是可逆的：密钥总得放在程序能拿到的地方（配置文件/代码里），拷库的人顺手就能拿到。正确问法不是「加密了吗」，而是「可逆吗」
Base64 / 简单编码看起来是一串乱码编码不是加密，零秘密可言，一秒还原
本课核心 合格的存储方案 = 不可逆 + 足够慢 + 每密码唯一盐。三个条件缺一个，库被拷走密码就守不住。这也回答了一个常见的错误直觉：「加密」从来不是密码存储的正确工具，单向哈希才是。

哈希也不保险：快，是致命伤

把密码做 SHA-256 再存，不可逆了，够了吗？不够——因为 SHA-256 快得离谱。现代显卡一秒能算几十上百亿次哈希，而对桌面软件来说攻击者拿到库文件后可以离线慢慢算，没有任何接口限速能拦他：

  • 暴力破解：8 位纯数字密码，对 GPU 是零点几秒的事——离线爆破没有任何人打扰。
  • 彩虹表：把常见密码的哈希预先算好存成巨型查找表，逐行查表还原，连算都不用算。
  • 同密码同哈希：不用破解，数一遍哈希值，就能看出哪些账号共用同一个密码——共用密码的那个往往就是管理员。

思路因此只有一个方向：把哈希故意弄慢——用户登录时多等几十毫秒无感，攻击者离线爆破每一条都要付出同样代价，而且没有捷径。

三件套：不可逆、盐、慢

  1. 单向哈希打底——不可逆，库丢不丢密码。
  2. 每密码唯一随机盐（salt）——16 字节随机值拼进密码再哈希，和哈希一起明文存，不需要保密：它防的是预计算。盐唯一之后，彩虹表整表作废，同密码的哈希也互不相同。校验时读出该用户自己的盐重算比对即可。
  3. 慢哈希（专用算法）——用专为密码设计的密钥派生函数（KDF）：首选 Argon2id（OWASP 建议至少 19 MiB 内存、2 次迭代、并行度 1）；PBKDF2-HMAC-SHA256 至少 600,000 次迭代（下文的 .NET 内置方案就是它）；bcrypt 成本因子 ≥10 可用但属保守选择。经验法则：单次哈希耗时应小于一秒——登录时用户感知不到，离线爆破却要付出同倍代价。

三个条件层层递进：哈希管不可逆，盐管「别让攻击者批量算」，慢哈希管「让暴力破解贵到不划算」。桌面软件没有任何理由少装一件——本地库恰恰是最容易离开你控制的东西。

在你的 WPF 里怎么落地

规则一：别自己发明——用现成的库。Microsoft.Extensions.Identity.Core 包里的 PasswordHasher 就是个普通类（内部 PBKDF2 + 自动盐 + 版本化格式），不需要 ASP.NET、不需要 Web 框架，桌面程序直接 new（官方 API 文档）：

// NuGet：Microsoft.Extensions.Identity.Core（纯类库，桌面/控制台都能用）
using Microsoft.AspNetCore.Identity;

var hasher = new PasswordHasher<object>(
    Options.Create(new PasswordHasherOptions { IterationCount = 600_000 }));  // 调到 OWASP 建议

// —— 注册用户（写进本地库的 Users 表）——
var user = new LocalUser {
    Name = inputName,
    Role = "操作员",
    PasswordHash = hasher.HashPassword(null, inputPassword)   // 盐自动生成，随哈希一起存
};

// —— 登录校验（登录窗口的确定按钮里）——
var saved = db.Users.FirstOrDefault(u => u.Name == inputName);
var result = hasher.VerifyHashedPassword(null, saved.PasswordHash, inputPassword);
// result == Success                 → 通过
// result == SuccessRehashNeeded     → 通过，但参数过旧 → 趁这次登录用新参数重哈希落库（无感升级）
// result == Failed                  → 密码错误

// 轻量替代：BCrypt.Net-Next 包
// 存：BCrypt.Net.BCrypt.HashPassword(密码, workFactor: 12)   验：BCrypt.Verify(密码, hash)
接入已有的旧密码列 如果现在的用户表已经是明文或快哈希，你并没有原密码可重算——不要停机批量迁移。标准做法是「登录时升级」：校验先走旧算法，通过后立刻用慢哈希重存（列上加个标记区分新旧格式）。用上几个月，活跃用户的密码就全换完了。SuccessRehashNeeded 就是给这个策略留的钩子。

课后作业：给密码列定一份技术方案

  1. 跑实验：在上方实验台点「演示：同密码无盐跑两次」和「演示：同密码加盐跑两次」，记下两次的结论；再把 PBKDF2 调到 600,000 跑一次，记下你机器上的耗时——这就是登录时真实的校验开销。
  2. 定参数：选定路线（PasswordHasher 调 60 万次，或 BCrypt cost 12），照实验台耗时确认登录无卡顿。
  3. 查存量：打开你家的用户表，看密码列现在存的是什么（明文 / 加密 / 哈希？什么算法？）。是旧格式的话，按「登录时升级」写一句迁移计划——如实记录，第 3 课的登录窗口就拿它开刀。

本课首选原文：OWASP Password Storage Cheat Sheet——各算法最小参数（Argon2id 19 MiB / 2 次 / 并行 1，PBKDF2-SHA256 ≥600,000 次等）的唯一权威出处。.NET 侧配套：Microsoft Learn — PasswordHasher<TUser>（桌面可直接用）。标准依据：NIST SP 800-63B-4（盐与慢哈希的要求原文）。
