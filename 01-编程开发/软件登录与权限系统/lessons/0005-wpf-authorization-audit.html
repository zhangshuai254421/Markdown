软件登录与权限系统 · 第 5 课（纯桌面版）

WPF 授权与审计落地第 4 课的矩阵画得再好，不接进命令和界面，就只是一张许愿表

第 4 课的权限矩阵描述了「应该怎样」，这一课回答「怎么在 WPF 里保证就是这样」。核心只有一句话：把权限检查集中在一处（权限服务），让命令的 CanExecute 和界面的显隐都来问它——而不是每个按钮各写一个 if，更不是把「谁能用什么」写死在代码里。OWASP 授权原则里的「默认拒绝」「最小权限」「检查集中」，在桌面形态全部翻译成这一层封装。

先分清：控制与体验

做什么为什么这么分
控制（逻辑层）命令的 CanExecute 返回 false → 按钮禁用、命令不执行这是真正的权限检查——执行路径上的一关，绕界面也绕不过命令
体验（视图层）菜单/Tab 按权限点显隐让不同岗位看到不同界面，少干扰少误点。它是同一份权限数据的另一种呈现，不是控制本身

两条用同一份权限数据（第 4 课那两张关系表），永远不要写两套判断——「菜单显示着但点了没反应」和「菜单藏了但命令没挂权限」都是两套判断打架的症状。

四件套落地

① 权限服务：唯一的检查点

public interface IPermissionService
{
    bool Can(string permissionCode);          // 查第4课的 RolePermissions 表
    IReadOnlySet<string> Codes { get; }       // 当前用户全部权限点，给界面绑定用
}

public class PermissionService : IPermissionService
{
    // 登录时按 UserSession.Current 的角色一次性加载，缓存成 HashSet
    private readonly HashSet<string> _codes;
    public PermissionService(IEnumerable<string> roleCodes) =>
        _codes = new HashSet<string>(roleCodes);
    public bool Can(string code) => _codes.Contains(code);   // 没有就是没有——默认拒绝
    public IReadOnlySet<string> Codes => _codes;
}

// RelayCommand / DelegateCommand（Prism）都支持 canExecute 参数
SaveParamsCommand = new RelayCommand(
    execute: SaveParams,
    canExecute: _ => _perms.Can("工艺参数-修改"));     // 第4课定义的权限点编码

private void SaveParams()
{
    // 执行前不必再查一次——CanExecute 已把住入口；
    // 但拿不准的地方多查一次也无妨：_perms.Can(...)
}

③ 界面：显隐绑定同一份数据（体验）

<!-- ViewModel 暴露 Perms.Codes，转换器决定显隐 -->
<MenuItem Header="用户管理"
          Visibility="{Binding Perms.Codes, Converter={StaticResource ContainsToVisibility},
                       ConverterParameter=用户管理}"/>

④ 审计：关键操作落一行

public void Write(string action, string target, string detail = "")
{
    db.AuditLogs.Add(new AuditLog {
        Time = DateTime.Now,
        UserName = UserSession.Current?.Name ?? "(未登录)",
        Action = action, Target = target, Detail = detail
    });
}
// 用法：_audit.Write("修改工艺参数", "温度上上限", "120 → 150");
// 四类必记（第1课第五环节）：改配置、删数据、登录成败、权限变更；「拒绝的操作」也记。

用 Prism 的话，把 IPermissionService 注册进容器（登录成功后构造一次，随 UserSession 生命周期），各 ViewModel 构造函数注入——检查点全局唯一，将来权限逻辑怎么改都只动一处。

桌面版的「越权」长什么样

服务端形态的越权是跨网络的请求伪造；桌面形态里这两个概念收敛成界面与数据的两问：

概念桌面语义对策
垂直越手（原「垂直越权」）操作员够到管理员的功能——多半是命令忘了挂 CanExecute入口清单逐个核对（见作业）；默认新命令不挂权限就先禁用
跨人看数据（原「水平越权」）报表/历史数据里看到不该看的班组、别人的记录查询逻辑按当前用户的数据范围过滤（如「只看本班组」），这是业务代码里的职责，不是界面显隐能解决的
诚实定位（第 1 课边界的最后一次重申） 进程内的权限检查挡的是正常用户的误操作和越手——这覆盖工厂里绝大多数真实需求。它挡不住能改本地库、补丁程序的人。把这句答案准备好：「需要更强边界时，权限与账号数据收进中央数据库（禁用/调权全局生效、审计离开本机），或加应用服务端。」你就比大多数同行诚实且专业。

课后作业：把权限接进命令

  1. 列入口：数出主界面全部「会改变什么」的按钮/命令，列成清单——这就是你家的入口表。
  2. 挂权限：实现 IPermissionService + 审计服务，给清单上每条命令挂上权限点（对照第 4 课矩阵），先从「修改工艺参数」和「删除数据」这两类挂起。
  3. 写审计：给挂好权限的三条命令补审计——登录成功、修改成功、修改被拒（CanExecute 为 false 的点击事件也值得记一条「尝试」）。
