一、线程池:一队工人,两个队列

线程很贵:约 1MB 级栈内存、内核对象、调度开销。于是运行时养了一队可复用的工人线程 (worker threads),配一个调度系统,这就是线程池。结构一句话:

部件职责
全局队列Task.Run(非池线程发起)排进这里 → 欠条状态 WaitingToRun(0005)
本地队列池线程里再 Task.Run/子任务,排进该工人的本地队列(快;还有"偷活"机制,细节问老师)
工人循环取任务 → 执行(Running)→ 完成 → 取下一个,永不主动下班
补充机制工人全忙时,缓慢注入新线程(约每半秒一个,受 SetMinThreads 影响)——记住这个速度,下面要用

结构表来自官方文档(托管线程池 — Microsoft Learn)。 关键在第 4 行:补充慢,消耗快,饥饿就发生了。工人被"干等"型任务占住 → 队列越排越长 → 新线程半秒一个地救场,杯水车薪 → 全池变慢。 0005 状态图里 WaitingToRun 堆积的病灶,机械原因在此。

由此推出线程池的经济模型

整个系统建立在"每个活很快干完、立刻还工人"的假设上。凡是占着工人不还的用法 ——干等 IO、同步阻塞、死循环——都是在放这个经济系统的血。

二、判决尺:先问"干活的是谁"

拿到一个任务,第一问不是"要不要 Task.Run",而是:

活的本性真正干活的正确姿势错误姿势的代价
CPU-bound(压缩、序列化、图像、算数)本机 CPUUI 应用里 Task.Run 挪走,防卡界面直接在 UI 线程算 → 界面冻结
IO-bound(网络、磁盘、DB、定时)外部设备/远端真异步 API,await——0 线程(0001 起的全部机制为此而生)Task.Run 包同步 IO → 占工人干等,慢性放血
判决尺落成代码 · 三不纪律
// × 不 1:Task.Run 包同步 IO(工人被派去"干等网络")
var html = await Task.Run(() => _httpClient.GetStringAsync(url).Result); // 更糟:见下

// ✓ 正确:真异步,零线程
var html = await _httpClient.GetStringAsync(url);

// × 不 2:库里替调用方决定并发(Task.Run 的调用权在应用层)
// ✓ 不 3 服务端:ASP.NET Core 里请求本来就跑在池工人上,Task.Run = 把活挪个位置还多付开销

0007 欠的账:sync-over-async 到底烧几个工人?

Task.Run(() => FooAsync().Result).Result 这一行: 外层 .Result 阻塞工人 A;内层委托在工人 B 上跑, 随即也被 .Result 阻塞。两个工人换一件活,且 A 纯属陪绑。 无上下文环境不死锁(0007 讲过),但池子被双倍放血——迁移期过渡可以,长期必删。

四、ValueTask 初识:热路径的第二种欠条

源码视角0006 讲过快速路径:欠条早已完成时,await 几乎免费—— 但"几乎"里还剩一笔:Builder.Task 那个 Task 对象本身,每次调用仍要分配。 高频调用(每秒几十万次的缓存读、协议解析)里,这笔账开始显眼。 ValueTask<T> 是答案:

Task / Task<T>ValueTask<T>
本体class,每次分配struct,栈上
同步完成路径仍分配一个 Task(0006 快速路径)直接包结果,零分配
异步完成时正常路径内部退化为包着一个 Task(不亏)
消费规则随便 await只能 await 一次
默认选择✓ 安全默认仅热路径
ValueTask 的标准形态:先查同步,未命中才异步
private readonly ConcurrentDictionary<string, byte[]> _cache = new();

public ValueTask<byte[]> GetDataAsync(string key, CancellationToken ct)
{
    if (_cache.TryGetValue(key, out var hit))
        return new ValueTask<byte[]>(hit);            // 命中:零分配直接还结果

    return new ValueTask<byte[]>(LoadCoreAsync(key, ct));  // 未命中:包住普通异步
}

private async Task<byte[]> LoadCoreAsync(string key, CancellationToken ct)
    => await _http.GetByteArrayAsync(GetUrl(key), ct);   // 真异步 IO:零线程(判决尺!)

ValueTask 三条使用纪律(违反 = 未定义行为级 bug)

① 只能 await 一次——不能存下来反复消费、不能并发 await;
② 完成前不混用——不要 await 之前又去 AsTask() 拆开两头用;
③ 只有"高频 + 常常同步完成"才值得——一般 API 用 Task, 它对调用方的宽容度(多次消费、WhenAll 组合)是真正的价值。
权威长文:Understanding ValueTask — Stephen Toub。 看到库返回 ValueTask,读出的潜台词是:"这是热路径,请遵守纪律。"
