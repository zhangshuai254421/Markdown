一、状态地图:三个区,八种状态

别背枚举表,先分区——每张 Task 的状态一定落在以下三个区之一:

区状态一句话
出生区(静止)Created手动 new Task<T>(...) 后、Start() 前的静止态;await 得到的任务几乎从不在此
运行区(活着)WaitingForActivation欠条已开出,等一个完成信号——TCS 任务的默认状态(0001 徽章!)
WaitingToRun已进入线程池队列,还没轮到工人
Running正在某个线程上执行
WaitingForChildrenToComplete父任务在等所有子任务完成(少见的中间态)
终态区(不可变)RanToCompletion成功完成;唯一令 IsCompletedSuccessfully 为 true 的状态
Faulted故障;await 处重新抛出异常
Canceled已取消;await 处抛 TaskCanceledException

两个贯穿前课的铁律:①终态三选一,进入即永久不可变(0002 讲过这正是广播安全的根基); ②出生区几乎只属于手动 new——async 方法、Task.Run、TCS 开出的欠条,出生即进入运行区。 下面亲手走一遍每条路径。

① TCS 欠条跳过了整个"排队/运行"区——它从不执行代码,所以出生即 WaitingForActivation, 直接等终态。这也是"Task ≠ 线程"最直观的证据:一个从 Running 里根本没出现过的东西,照样能完成。

四、Canceled 与 Faulted 的分界线(高级考点)

面试高频同样一个 OperationCanceledException(OCE), 官方 TAP 规则决定终态落在哪一侧:

TAP 规则 · OCE 的去向他处
// async 方法抛出 OCE → 任务进 Canceled(不是 Faulted!)
async Task WorkAsync()
{
    await Task.Delay(10);
    throw new OperationCanceledException();
}
// workTask.Status == Canceled;await 抛 TaskCanceledException

// 对照:抛普通异常 → Faulted
async Task Work2Async()
{
    await Task.Delay(10);
    throw new Exception("boom");
}
// work2Task.Status == Faulted;await 抛原异常

由此推出的工程纪律

别拿 OCE 当普通业务异常抛——它会把任务送进 Canceled,让调用方和监控都误以为"这是取消"。 反过来,await 收到 TaskCanceledException 时也别 100% 断定"是别人取消了我"。 规则原文见 TAP 规范;令牌匹配的细节边角值得动手验证(或直接问老师)。
