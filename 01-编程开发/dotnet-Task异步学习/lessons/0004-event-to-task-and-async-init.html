事件流→Task 与异步初始化

⏱ 预计 20–25 分钟 前置:第 0001–0003 课 交付:事件等待骨架 + 单飞初始化(连接就绪模式)

前三种模式解决的都是"回调式"API:结果必定会来一次。但更多库是 事件式的——事件可能触发 0 次、1 次或 N 次,时机完全不由你控制。 "等连接建立再发消息""等初始化完成再用客户端"——今天这两个骨架, 就是 SignalR、消息队列客户端里"等待就绪"的通用写法。

一、模式一:等一次性事件发生

场景:消息客户端 SDK 只提供 Connected 事件,你想给同事一个干净的 await WaitForConnectedAsync()。骨架四步,每一步都有理由:

事件 → Task · 黄金骨架
public Task WaitForConnectedAsync()
{
    var tcs = new TaskCompletionSource(
        TaskCreationOptions.RunContinuationsAsynchronously);

    void OnConnected(object? s, EventArgs e)
    {
        _client.Connected -= OnConnected;    // ① 到达即退订——防泄漏
        tcs.TrySetResult();                  // ② Try*——取消等路径在竞争
    }

    _client.Connected += OnConnected;        // ③ 先订阅……

    if (_client.IsConnected)                 // ④ ……后检查(顺序是命门)
    {
        OnConnected(_client, EventArgs.Empty);  // 已连接:复用同一清理逻辑
    }

    return tcs.Task;
}
步骤为什么非它不可
③ 先订阅若先检查再订阅,事件可能在两行代码之间触发——没人接住,await 永久悬挂
④ 后检查事件可能在你订阅之前就已经发生过了("已发生"检查是兜底,不是可选项)
① 到达即退订事件源(客户端对象)活得比欠条久;lambda 捕获着 tcs,不退订 = 整条引用链泄漏
② 用 TrySet*"已连接"分支与事件分支可能竞争,后到者须安静放弃(0002 的竞速语义)

源码视角这就是框架"等待就绪"的骨架

各连接库"等待握手完成/传输激活"的内部实现,基本都是这四步加上 0003 的令牌传播 (取消时也要退订——完整生产版含取消,见文末速查卡)。官方把"事件模式(EAP)"包装成 Task 的推荐做法同样是 TCS,见 TAP 规范的互操作章节。

二、动手玩:亲手放跑一次事件

这个 bug 极其隐蔽,不如现在就犯一次。操作顺序:

实验 1:先点 ⚡(事件触发),再点 A 版 → 看它如何永久悬挂。
实验 2:重置,先点 ⚡,再点 B 版 → 看它如何安全返回。
实验 3:重置,先点 A 版(未连接,挂起),再点 ⚡ → 观察两种写法被唤醒的过程。

实验后对照答案

① A 版的悬挂发生在"检查(false)→订阅"之间:事件已放走,订阅等来的是永远。
② B 版因为先站好位置,无论事件来早来晚都能接住:来晚了走处理器,来早了走检查兜底。
③ 记住顺序口诀:先订阅,后检查;到达即退订;销账用 Try。

三、模式二:单飞异步初始化

面试高频场景升级:连接不仅要"等",还要"建立"——而建立是异步的, 构造函数里不能 await。全项目的代码都要等它就绪。怎么设计?

天真版的坑:每个调用点都 if (!ready) await ConnectAsync()——两个请求同时发现未连接, 并发建立两条连接,第二条白白泄漏。标准解法叫单飞(single-flight), 核心又是 TCS:

单飞初始化 · 一张欠条,所有人在等
private TaskCompletionSource<MessageClient>? _initTcs;

public Task<MessageClient> GetClientAsync()
{
    if (_initTcs is null)
    {
        var tcs = new TaskCompletionSource<MessageClient>(
            TaskCreationOptions.RunContinuationsAsynchronously);

        if (Interlocked.CompareExchange(ref _initTcs, tcs, null) is null)
        {
            _ = InitializeAsync(tcs);      // 只有抢到写入权的调用者启动初始化
        }
    }

    return _initTcs.Task;                   // 后来者直接 await 同一张欠条(0002 广播语义)
}

private async Task InitializeAsync(TaskCompletionSource<MessageClient> tcs)
{
    try
    {
        var client = await CreateAndConnectAsync();
        tcs.SetResult(client);             // 无竞态:唯一完成路径 → 用 Set*(断言,0002)
    }
    catch (Exception ex)
    {
        tcs.SetException(ex);              // 失败也广播:所有等待者立刻拿到异常
        _initTcs = null;                   // 惯例:置空,允许下次调用重新尝试
    }
}
设计点理由
Interlocked.CompareExchange 抢写入权无锁保证"只有一个初始化启动者",其余并发调用者全部汇入同一张欠条
完成路径唯一 → SetResult没有竞争者,沿用"无竞态用 Set\*,让 bug 显形"的决策
失败时 _initTcs = null失败不该被缓存成永久状态;下次调用重新尝试,符合直觉
所有人都 await 同一个 .Task欠条终态不可变 → 广播安全(0002 的"为什么")在这里变现

源码视角这个模式的亲戚们

轻量替代:Lazy<Task<T>>(少了失败重试);标准件:Stephen Cleary 的 AsyncLazy 与 Visual Studio 内部使用的 Microsoft.VisualStudio.Threading.AsyncLazy; ASP.NET Core 里"等 HostedService 启动完成"的机制同属这一家。 本课手写版的价值:每一行你都明白为什么存在。

四、检索练习(不看上文,凭记忆答)

五、明天的回忆任务(30 秒,不翻书)

① 事件等待为什么必须"先订阅,后检查"? 若先检查后订阅,事件可能在两行之间触发,没人接住,await 永久悬挂。先站位置,检查只是兜底。
② 到达即退订,防的是什么? 事件源活得比欠条久,lambda 捕获 tcs 不放——不退订整条引用链泄漏。
③ 单飞初始化失败后的惯例处理? 把异常广播给所有等待者,然后置空状态允许下次重试——不缓存失败。
