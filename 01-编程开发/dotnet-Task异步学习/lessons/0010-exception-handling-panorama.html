一、两套规则:await 解包,Wait/Result 打包

同一张故障欠条,两种消费方式,接到的异常形状不同:

消费方式抛出的形状多个异常时
await task原始异常(解包,不带包装)只抛第一个(WhenAll 场景)
task.Wait() / task.ResultAggregateException(打包)全部装在 InnerExceptions
GetAwaiter().GetResult()原始异常(行为同 await,但仍是同步阻塞)只抛第一个
task.Exception(属性)AggregateException?(不抛,取出来看)全部可见——WhenAll 拆包靠它
一张欠条,两种接法
Task<string> task = GetTextAsync();     // 假设它将抛 TimeoutException

try { var s = await task; }
catch (TimeoutException ex) { /* ✓ await:直接接到原始异常 */ }

try { var s = task.Result; }
catch (AggregateException agg) { /* Wait/Result:包了一层,要 .GetBaseException() */ }

为什么有两套?

历史层次:Task 诞生于 TPL 时代,消费端是 Wait/Result,打包便于一次携带多个; async/await 时代追求"异步代码读起来像同步",于是 await 帮你解包—— catch 里看到的和同步代码抛出的形状一致。这也是"async 方法内用 await 而不是 Result"的 又一理由:不接包装,还顺带躲开死锁(0007)。

二、WhenAll 的全异常拆法(0009 的坑,今天填)

0009 说过:WhenAll 把多张欠条的异常聚合成 AggregateException,但 await 只重抛 第一个。要全部拿到的标准姿势——先留住合成欠条本体,再拆 .Exception:

全异常拆包 · 标准模板
Task<int>[] jobs = ids.Select(id => CountAsync(id)).ToArray();
Task<int[]> all = Task.WhenAll(jobs);          // ① 先留住合成欠条本体!
try
{
    int[] results = await all;                 // ② 正常路径拿结果
}
catch (Exception)
{
    // ③ 异常路径:从本体拆出全部异常(await 只给了你第一个)
    foreach (var ex in all.Exception!.InnerExceptions)
        _logger.LogError(ex, "任务失败");
}

易错点

直接 catch (AggregateException) 接 await Task.WhenAll(...) 是接不到的—— await 已经把包拆了,你手里的是第一个原始异常。拆包的前提是先留住 WhenAll 返回的那张合成欠条(模板第①行)。另:Flatten() 可把嵌套聚合拍平, Handle(pred) 可批量筛掉已处理的。

三、ExceptionDispatchInfo:把异常存起来,原栈重抛

源码视角第三个角色回答一个特定问题: "异常能不能先存起来,过一会儿在别处再抛?"可以,而且必须用对工具:

写法堆栈适用
throw;保留当前堆栈catch 块内原样上抛——日常首选
throw ex;重置为这一行(原始堆栈丢失)几乎总是错误,代码评审直接打回
ExceptionDispatchInfo.Capture(ex).Throw()保留原始完整堆栈存起来日后再抛(跨方法/跨线程)
catch (Exception ex) when (条件)过滤不中 = 像没 catch 过,自然上飞精准过滤;不中时零开销不重置
EDI 标准用法
Exception? saved = null;
try { await RunAsync(); }
catch (Exception ex) { saved = ex; }          // ① 先存

// ……稍后、别处(另一个线程 / 清理路径 / 重试框架)……
if (saved is not null)
    ExceptionDispatchInfo.Capture(saved).Throw();   // ② 原栈重抛,不失真

连回 0006:重抛不失真的幕后功臣就是它

故障欠条在 await 处重抛异常时,内部正是用 EDI 把当初存入的异常原栈抛出—— 否则你看到的堆栈会是 GetResult() 那一行,而不是真正的案发现场。 异常的"打包"(Task 存 AggregateException)与"重抛"(EDI)都藏在 0006 那个骨架之下。

四、全景收拢:五条异常纪律

  1. async 代码里用 await 接,不用 Result/Wait——接原始形状,顺带躲死锁(0007)。
  2. 要 WhenAll 的全部异常,先留合成欠条再拆 .Exception——模板见第二节。
  3. 绝不 throw ex;要上抛用 throw;要异地重抛用 EDI——堆栈是案发现场,别毁。
  4. 过滤用 catch when,不用 catch 再判断——不中时堆栈与性能都干净。
  5. 别拿 OCE 当业务异常,async void 的异常没人能接——0005 的 Canceled 规则 + 0001/0007 的 async void 坑,一条线收拢:异常要么被欠条运到 await 处,要么逃出体系。

① await 与 Result 接异常,形状差在哪? await 解包抛原始异常;Result/Wait 打包抛 AggregateException。多异常时 await 只给第一个。
② WhenAll 要拿全部异常,标准三步? 先留合成欠条本体 → await 正常拿结果 → catch 后从 all.Exception.InnerExceptions 拆全部。
③ throw / throw ex / EDI 三者的堆栈差异? throw 保留;throw ex 重置成当前行(几乎总是错);EDI 保存后原栈重抛——欠条重抛内部用的就是 EDI。
