0001 课埋过一颗雷:如果硬件永远不回调,欠条永久悬挂,await 到天荒地老, 闭包引用都释放不掉。解药就是超时。但这一课真正想让你带走的,是一个绝大多数 .NET 老手都会答错的认知:超时只是"我不再等了",它不会叫停底层操作。

〇、隔日检索(先测后学:0002 还剩多少?)

一、给 await 加超时:三式演化

第一式:WhenAny + Task.Delay(最常见的老写法)

WhenAny 版 · 到处可见,但有暗病
var work = bridge.ReadTemperatureAsync();
var winner = await Task.WhenAny(work, Task.Delay(TimeSpan.FromSeconds(5)));

if (winner != work)
    throw new TimeoutException("设备读取超时");

double temp = await work;   // 已完成,立刻返回

能用,但三个暗病:①成功路径上,那个 Task.Delay 和它的计时器仍存活到 5 秒触发为止(轻微资源滞留);②样板冗长,每个调用点都要复制这套判断;③它同样不取消底层操作——只是看起来像取消了。

第二式:手写 TCS + Timer(0002 预告的生产版)

把 0002 竞态安全模板里的超时兜底抽成可复用方法——这是 .NET 6 之前的标准答案(简化自 Stephen Cleary 的经典 WithTimeout):

手写 WithTimeout · 理解它,胜过背诵它
public static async Task<T> WithTimeout<T>(Task<T> task, TimeSpan timeout)
{
    var tcs = new TaskCompletionSource<bool>(
        TaskCreationOptions.RunContinuationsAsynchronously);   // ① 续延隔离(0002)

    using var cts = new CancellationTokenSource(timeout);      // ② 到点自动触发
    using var reg = cts.Token.Register(
        () => tcs.TrySetResult(true));                          // ③ 超时 → Try* 销账(0002 竞速语义)

    if (task != await Task.WhenAny(task, tcs.Task))
        throw new TimeoutException();

    return await task;                                          // ④ 已完成:返回值或原异常
}

四行注释正好是前三课的全部知识点——你现在已经能逐行读懂这段"框架级"代码了。 但手写终究要自己管生命周期,于是有了官方版:

第三式:.NET 6+ 一行搞定(WaitAsync)

官方捷径 · 日常首选
double temp = await bridge.ReadTemperatureAsync()
                             .WaitAsync(TimeSpan.FromSeconds(5));

// 重载:可再叠加外部取消令牌
await work.WaitAsync(TimeSpan.FromSeconds(5), cancellationToken);

API 依据:Task.WaitAsync(Microsoft Learn)——.NET 6 加入,三个重载(仅超时 / 仅令牌 / 两者)。

方案样板量泄漏风险超时抛出能中止底层?
WhenAny + Delay每处 5 行成功路径延迟任务滞留自己 throw❌
手写 WithTimeout封装一次低(Dispose 干净)TimeoutException❌
WaitAsync一行无TimeoutException❌ ←注意!

看清最后一列了吗?三种方案全都只是"弃等"(abandon the wait),没有一个能叫停底层。 这就引出本课的主菜。

二、主菜:超时 ≠ 取消

面试高频WaitAsync 超时那一刻,底层任务发生了什么? 什么都没发生。它继续跑,直到自己完成。变的只有消费者:await 抛出 TimeoutException,调用方离开,不再有人等那张欠条。底层的迟到结果将来会被 Try\* 竞速语义安全丢弃——0002 的伏笔在这里回收。

三、动手玩:超时时间线

播放下面的时间线,分别用"3 秒"和"8 秒"两档,观察消费者与底层工作各自的时间线:

实验 1:工作耗时 3 秒 → 赶在超时前完成,注意计时器释放。
实验 2:切到 8 秒再播放 → 注意 5 秒处消费者离开、8 秒处结果被丢弃。

这意味着什么(生产事故级)

如果你的"底层操作"持有连接、文件句柄、或会写数据库——超时之后它还在跑。 高并发下大量超时请求各自留着一个仍在执行的操作,资源占用不降反升,这就是"明明加了超时, 服务器还是被打挂"的经典原因。弃等救的是调用方,救不了服务器。

四、想要"真叫停"?令牌必须贯穿底层

取消是一条独立的机制(CancellationToken),必须显式传给底层操作才能生效。 超时只是给取消的一种"定时触发器":

真取消 · 令牌贯穿到 HttpClient 内部
using var cts = new CancellationTokenSource(TimeSpan.FromSeconds(5));  // 5 秒后令牌自动触发

try
{
    // 令牌一路传进底层 → 超时那一刻,HTTP 请求被真正中止,连接被释放
    var resp = await httpClient.GetAsync(url, cts.Token);
}
catch (OperationCanceledException) when (cts.IsCancellationRequested)
{
    // 惯用法:只把"这次超时"翻译成 TimeoutException,别的取消照常上抛
    throw new TimeoutException("请求超过 5 秒,已中止");
}
触发方式await 抛出识别要点
task.WaitAsync(TimeSpan) 超时TimeoutException明确表达"是超时"
CancellationTokenSource 到点 / 手动 Cancel()TaskCanceledException(OperationCanceledException 子类)"是取消"——超时取消和其他取消在此混在一起,需 catch-when 辨别

取消机制官方指南:Managed Threading · Cancellation(Microsoft Learn)。

面试高频"如何给异步 API 加超时"的三层满分答案

① 调用方弃等:await task.WaitAsync(TimeSpan);
② 真中止:令牌贯穿底层(CTS(TimeSpan) + 把 token 传下去),超时才真正释放资源;
③ 收尾:超时后底层的迟到结果如何处置(丢弃要幂等;可取消的清理动作)。
能答出①的很多,能答全②③的,就是面试官眼里"真懂异步"的人。

五、实战:0001 那颗雷,终于排掉了

硬件 SDK 没有取消接口(老设备常如此),所以只能"弃等 + 竞速丢弃"——但这已经完整正确:

生产级桥接 · 三课知识合体
// 库内(0002 的竞态安全版,不变)
public Task<double> ReadTemperatureAsync()
{
    var tcs = new TaskCompletionSource<double>(
        TaskCreationOptions.RunContinuationsAsynchronously);

    _sensor.ReadTemperature(
        onSuccess: v  => tcs.TrySetResult(v),
        onError:   ex => tcs.TrySetException(ex));

    return tcs.Task;
}

// 调用端(本课):5 秒内必有答案 —— 结果,或 TimeoutException
double temp = await bridge.ReadTemperatureAsync()
                             .WaitAsync(TimeSpan.FromSeconds(5));
// 若硬件 8 秒后才回,迟到结果被 TrySet* 语义安全丢弃,无泄漏、无异常噪音。

七、明天的回忆任务(30 秒,不翻书)

① WaitAsync 超时后,底层操作死了吗? 没死。它继续跑到自然完成,迟到的结果被竞速语义丢弃。超时只是弃等。
② 想真正中止底层操作,怎么做? CTS(TimeSpan) 产生令牌并传进底层调用(如 GetAsync(url, token));令牌触发才会真中止、真释放。
③ WaitAsync 超时与令牌超时,抛的异常有何不同? 前者 TimeoutException;后者 TaskCanceledException / OperationCanceledException——需要 catch-when 区分。
