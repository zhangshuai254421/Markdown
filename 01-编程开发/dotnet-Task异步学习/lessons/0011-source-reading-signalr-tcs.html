一、为什么拿 SignalR 开刀

SignalR 客户端每调用一次服务端 Hub 方法(InvokeAsync),都要经历:

  1. HTTP/WebSocket 消息发出去,回复不知道什么时候来、从哪个线程来;
  2. 必须立刻给调用方一个可以 await 的东西——这不就是欠条吗;
  3. 回复到达时按编号找到对应欠条销账;超时、取消、断线各自有收场方式。

这就是 0001 课"回调→Task 桥接"的工业级版本,而且是活的: ASP.NET Core 官方仓库、每天被百万应用依赖的代码。

三、实战地图:把课程术语钉在源码上

精读笔记(以链接到的当前源码为准)

行号会漂移、文件可能搬家——找不到就退回符号搜索,这本身就是精读训练的一部分。 下表右列是我读到的对应关系,你要做的是亲手把它们一个一个"认领"。

源码现场课程术语
new TaskCompletionSource<object?>(TaskCreationOptions.RunContinuationsAsynchronously)(InvocationRequest)0001 开票 + 0002 坑①:防销账线程被续延同步拖住
_pendingInvocations.TryAdd(invocationId, …)欠条编号 + 挂号处;Try = 重号/竞态时体面失败(0002)
回复消息到达 → TrySet*(找找看,是 Try 不是 Set)销账纪律:超时/取消可能抢先(0002/0003)
断线 → 批量失败所有 pending 欠条广播终态(0004):不能让任何欠条永挂
CancellationToken 注册 → TrySetCanceled + 摘除登记取消分支 + 先订阅后检查(0004/0005)

读源码最常见的误读

看到 TrySetResult 就问"失败时为什么不抛?"—— 错位了:Try 的返回值不是"业务成功", 而是"销账权是否还归我"。抢不到销账权(超时已判、欠条已销)是正常路径, 不是异常。把"机制层竞争"和"业务层成败"分开,源码瞬间清爽。

四、寻宝作业(打开链接,亲手找答案)

① InvocationRequest 的 TCS 构造参数是什么?为什么非加不可? 提示:看构造函数;RunContinuationsAsynchronously——没有它,读循环线程销账时续延可能同步执行, 调用方一个慢回调就拖住整个消息泵(0002 坑①)。
② 回复到达时,销账用 Set 还是 Try?谁可能抢先? 提示:在消息处理路径搜 TrySet;超时/取消/断线都可能是"先判官"——竞态纪律(0002)。
③ _pendingInvocations 是什么类型?key 是什么?为什么必须是并发容器? 提示:invocationId(string)→ 欠条;开票(UI 线程/调用方)与销账(读循环线程)不同线程。
④ 断线时,挂号处里还没销账的欠条怎么收场? 提示:找 OnDisconnected / 批量失败路径——任何欠条都不许永挂(0004 广播终态)。
⑤ 指出一条"若无 RunContinuationsAsynchronously 就可能卡顿/死锁"的具体代码路径。 提示:从"读循环线程收到回复"出发,推演续延同步执行时会占用谁——找到最优的一条,讲给老师听。
