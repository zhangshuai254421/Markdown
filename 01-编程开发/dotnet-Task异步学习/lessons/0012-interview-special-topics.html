二、三大高频题 · 60 秒答法

题一:异步死锁为什么发生?(0007)

60 秒脚本
// 面试白板题标配代码
private async void Button_Click(...) => // UI 事件
    _label.Text = LoadData().Result;    // × 同步阻塞,环在此闭合

private async Task<string> LoadData()  // 默认捕获 UI 上下文
    => await _http.GetStringAsync(url); // 续延要 Post 回 UI 队列

因果链四节点:UI 线程 .Result 阻塞自等 → 欠条要等续延执行完 → 续延被 Post 回 UI 队列 → UI 线程不泵消息。破环两个方向: 应用层一路 async(await LoadData());库层 ConfigureAwait(false) 让续延不再回投。 陷阱题防身:ConfigureAwait(false) 只管这一个 await 的续延,不传染(0007 三事实)。

题二:sync-over-async 错在哪?(0007 + 0008)

定义:同步代码里等待异步操作(.Result / .Wait() / GetAwaiter().GetResult())。

代价机理
死锁风险存在同步上下文时,四节点环成立(题一)
白烧线程欠条体系本可零线程等待;同步阻塞却钉死一个工人(0008 烧工人账本)
饥饿放大sync-over-async 占用快于线程池补充(约半秒补一),队列积压 → 全站变慢(0005/0008)

修复次序:能改签名就一路 async;不能改(遗留边界)就隔离封装 + 明知代价 + 服务端上下文为 null(async framework)时至少不死锁,但烧线程照旧。

题三:Task vs Thread vs ValueTask?(0001 + 0008)

ThreadTaskValueTask
本质OS 线程句柄(工人本身)欠条(可 await 的并发单元)结构体欠条(省分配的 Task 替身)
调度自己掌管生命周期线程池 / IO 完成端口同 Task 或同步完成
结果无返回值,靠共享状态Task<T> 直接 await同 Task<T>
成本创建贵(MB 级栈)堆分配一次同步命中时零分配
适用专用长活线程(消息泵/常驻监听)默认选择,可组合仅热路径高频同步命中

一句话总结:默认 Task;要一个专属工人常驻才 new Thread; 热路径且常同步完成才 ValueTask——且记住三纪律:只消费一次、完成前不混用、别存字段(0008)。
