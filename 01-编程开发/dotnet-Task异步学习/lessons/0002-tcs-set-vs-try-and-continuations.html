一、Set* 是断言,Try* 是容错

五件套里每个 Set 都有一个 Try 兄弟。决策不是"哪个更安全用哪个",而是看场景里是否存在合法的竞争者:

场景用哪个为什么
只有一条路径能完成欠条(如 0001 的硬件回调桥接) Set* 若真的发生二次完成,那必然是逻辑 bug——让它当场炸出来,而不是被静默吞掉
存在合法的竞争者(超时兜底、取消信号、多个事件源) TrySet* "谁先到谁赢,后到的放弃"是预期行为,返回 false 按分支处理即可

面试高频反模式:无脑全用 TrySet*

"Try 更安全"是常见的错误直觉。在没有竞态的场景用 TrySet*, 等于把"同一欠条被完成两次"这种 bug 的报警器拆了——它照常运行,只是永远不响。 Set* 抛异常不是缺陷,是断言(assert);Try* 是容错(tolerance)。 面试里能讲出这个权衡,比背 API 签名高一个层级。

语义依据:SetResult(Microsoft Learn)——"若 Task 已处于终态,此方法抛 InvalidOperationException"。

二、动手玩:两条路径抢一张欠条

场景升级:在 0001 的硬件读取上加了超时兜底——结果路径与超时路径都在等销账机会。 请做三个实验:

实验 1:先点"结果到达",再点"超时到点"→ 观察后者的返回值。
实验 2:重置后反过来,先"超时"后"结果"→ 观察赢家换了人,消费者收到什么。
实验 3:完成后再连点任意按钮 → 确认再也不会抛异常,只是安静地返回 false。

实验后对照答案

① 后到的路径 TrySet* 返回 false,不抛异常、无副作用——这就是容错语义。
② 谁先到谁赢:超时赢了,消费者只会看到 TimeoutException;迟到的结果被直接丢弃。
③ 完成后一切 Try 调用都安全返回 false——竞态代码因此不需要加锁来"保护"销账动作,Task 终态自身就是原子裁判。

三、为什么"只能销一次"?——不可变性即线程安全

源码视角把 0001 的"欠条只能销一次"和本课实验合起来看,一个设计意图浮出水面: Task 一旦进入终态(成功/异常/取消)就永久不可变。正因为不可变:

① 一张欠条可以放心地交给 N 个消费者 await——大家读到的都是同一条不可变事实;
② 销账的竞争不需要调用方加锁——Task 内部自带的原子状态切换就是裁判;
③ 消费者可以"随时加入"——即使欠条早已销账,新来的 await 也会立刻拿到结果。

这也是为什么框架敢把 tcs.Task 作为公共属性暴露给任意多的内部模块。 深入机制可读 Stephen Toub 的 Async/Await FAQ。

四、续延去哪了?——默认内联与它的代价

现在回答第二个悬念。消费者 await 挂起后,当生产者调用 SetResult 的那一刻, await 之后的代码(续延,continuation)默认就在"调用 SetResult 的这条线程"上直接执行—— 不排队、不切换,像普通函数调用一样"顺路"跑掉。术语叫内联(inline)执行。

默认:内联 续延直接在完成者线程上跑完才返回 Set* 那一行
vs
RunContinuationsAsynchronously 续延排队到线程池,Set* 立刻返回,两者不再纠缠

内联是有意的性能优化(省一次线程池调度)。但它有个危险的前提: 完成者线程"顺路"执行的其实是消费者写的任意代码。看这个真实的重入死锁:

危险写法 · 持锁销账(可运行的陷阱)
private readonly object _gate = new();
private TaskCompletionSource<int>? _pending;

public void OnExternalEvent(int value)
{
    lock (_gate)
    {
        _pending?.SetResult(value);
        // ⚠ 默认内联:await 之后的消费者代码【此刻就在你的锁里】执行
    }
}

// 消费者某处:
var v = await _pending.Task;      // 恢复时机 = 上面 SetResult 那一行,且在锁内
DoSomething(v);                   // 若这条调用链上任何地方再想拿 _gate → 死锁

就算不死锁,完成者线程(比如一个高频消息接收循环)也会被消费者的慢代码劫持。 解法是构造时的一行选项:

修复 · 构造时声明"续延不内联"
var tcs = new TaskCompletionSource<int>(
    TaskCreationOptions.RunContinuationsAsynchronously);
// 续延改为排队到线程池:Set* 立刻返回,锁立刻释放,两者解耦。
// 代价:多一次线程池调度(纳秒~微秒级)。隔离换性能,几乎总是划算。

源码视角框架作者的肌肉记忆

在 ASP.NET Core、SignalR、Npgsql 等库的源码里,几乎每个 TaskCompletionSource 构造都带着 RunContinuationsAsynchronously——库作者无法预见消费者续延会干什么, 默认隔离是防御性设计。你现在去反编译工具里验证,会成为你读源码时的一个"认路标记"。 选项语义见 TaskCreationOptions(Microsoft Learn)。

五、实战拼图:升级 0001 的桥接模板

把本课两个技能组装进 0001 的硬件桥接——竞态安全版:

竞态安全版桥接 · Try* + RunContinuationsAsynchronously
public Task<double> ReadTemperatureAsync()
{
    var tcs = new TaskCompletionSource<double>(
        TaskCreationOptions.RunContinuationsAsynchronously);  // ① 续延隔离

    _sensor.ReadTemperature(
        onSuccess: v  => tcs.TrySetResult(v),   // ② 有超时兜底在竞争 → 用 Try*
        onError:   ex => tcs.TrySetException(ex));

    // ③ 超时兜底:5 秒后与结果路径竞速(生产级写法下一课展开)
    var timer = new System.Threading.Timer(
        _ => tcs.TrySetException(new TimeoutException("设备未响应")),
        null, dueTime: 5000, period: Timeout.Infinite);

    return tcs.Task;
}

// 调用端:5 秒内必返回 —— 要么拿到温度,要么拿到 TimeoutException
double temp = await bridge.ReadTemperatureAsync();

对比 0001 的版本,三处升级正好对应本课三个知识点:①防劫持、②容错竞速、③消灭"永久悬挂"陷阱。 下一课(0003)我们会把③重写成生产级形态,并对比 .NET 6 的官方捷径 task.WaitAsync(TimeSpan)。

七、明天的回忆任务(30 秒,不翻书)

① TrySetResult 返回 false 意味着什么?此时应该抛异常吗? 欠条已被别的路径抢先销账。不抛——false 是竞态中的预期分支,不是错误。
② 默认情况下,续延在哪个线程执行?风险是什么? 内联在调用 Set* 的完成者线程上。风险:消费者代码劫持完成者线程;持锁销账时可造成重入死锁。
③ 什么时候给 TCS 构造加 RunContinuationsAsynchronously? 库代码/无法预见续延行为时、持锁销账时、完成者线程有实时性要求时——默认隔离几乎总是对的。
