DOTNET · TASK SYSTEM · 第 0001 课

Task 是一张欠条:亲手握住"销账权"

⏱ 预计 20 分钟 前置:会用 async/await 即可 交付:欠条心智模型 + 回调转 Task 模板

你写过几千次 await。但停下来想一个问题:Task 到底是什么? 它不是线程,不是"正在跑的任务",甚至本身不执行任何代码。它只是一张欠条(IOU)—— 一张写着"未来某个时刻,会有一个结果"的凭据。而 TaskCompletionSource(下称 TCS), 就是让你亲手写下并销掉这张欠条的那支笔。

一、欠条的两半

每张 Task 欠条都有两半,分属两个角色:

生产者 Producer 出票人:承诺"结果会来",并在结果到来时调用 Set* 销账
SetResult()
完成欠条
Task 欠条 一张凭据:完成前"什么都没有",完成后携带结果/异常/取消
await
登记续延
消费者 Consumer 持票人:await 欠条,完成后恢复执行(即"续延")

关键认知有三个,先记住,后面的模拟器会逐一验证:

① 欠条完成前,里面什么都没有——没有值、没有线程、没有"正在计算的东西"。
② 同一张欠条可以给很多人持有了等待(多个 awaiter),但销账只能有一次。
③ 谁销账,await 后面的代码默认就在谁的线程上继续跑。

依据:官方 TAP 规范将 Task 定义为"一个将来可用的操作的占位符"—— Task-based Asynchronous Pattern(Microsoft Learn)。

二、Task 从哪来?——四种"出票人"

你每天见到的 Task,都来自下面四条产线。区别只在:谁替你握着销账权。

出票方式销账人是谁典型场景
async 方法 编译器生成的状态机(替你出票) 你自己的业务逻辑
Task.Run(...) 线程池工人干完活后出票 CPU 密集计算
BCL 的 IO 类(HttpClient、FileStream…) 操作系统完成通知后出票 网络、磁盘等 IO
TaskCompletionSource 你自己,在任意时机、任意线程 包装回调 API、超时控制、事件桥接

看清这张表,一句话就立起来了:async/await 和 Task.Run 都只是"出票"的便利封装; TCS 才是出票权本身。你以前觉得 TCS 高级,只是因为前三种都替你把笔拿好了。

源码视角为什么每个框架里都有 TCS

SignalR 等待连接建立、ASP.NET Core 等待请求生命周期事件、gRPC 等待流关闭——这些场景的共同点是: "完成"这个事件由外部世界触发,框架必须亲手控制欠条何时销账。 前三种出票方式都做不到"由我决定何时完成",只有 TCS 可以。 你可以现在就验证:在任意反编译工具里搜 TaskCompletionSource,数不过来。

三、TCS 初见:五件套

最小可运行示例 · Console
var tcs = new TaskCompletionSource<string>();

// 消费者:await 这张欠条(此刻没有任何线程被阻塞)
var printTask = Task.Run(async () =>
{
    var result = await tcs.Task;          // 暂停,让出线程
    Console.WriteLine($"收到: {result}"); // ← 这行是"续延"
});

Console.WriteLine("欠条已开出,还没销账…");

tcs.SetResult("欠条已还");                 // ← 生产者销账,续延立刻恢复

await printTask;

五件套全貌(本课只需认识,第 0002 课逐个深挖):

成员作用一句话关键细节
.Task取出欠条读一百次都是同一个 Task,可交给任意多人 await
SetResult(v)成功销账只能调一次;重复调用抛 InvalidOperationException
SetException(ex)记坏账await 处会重新抛出这个异常,而不是返回默认值
SetCanceled()注销await 处抛 TaskCanceledException
TrySet*(...)安全版销账返回 bool 不抛异常;竞态场景(如已有超时兜底)用它

API 依据:TaskCompletionSource<TResult>(Microsoft Learn)。顺带一提:.NET 5+ 还有非泛型版 TaskCompletionSource,专门产无值欠条 Task。

四、动手玩:验证三个关键认知

下面是一个可交互模拟器,左边是生产者,右边是消费者。请按顺序做三个实验:

实验 1:直接点绿色按钮 SetResult → 观察 Task 状态和消费者何时"活过来"。
实验 2:重置后点红色按钮 SetException → 观察异常如何送到 await 处。
实验 3:重置、完成一次后,再点 再 Set 一次 → 记住那个异常的名字。

实验后对照答案

① 完成前消费者不占任何线程——await 暂停时,线程早回线程池干别的活了("异步等待"的精髓)。
② 异常销账时,await 处重新抛出原异常——欠条上记的是坏账,不是默认值。
③ 二次销账抛 InvalidOperationException——欠条只能销一次,这是 TCS 的铁律。

五、实战模板:把回调 API 变成 awaitable Task

面试高频这是 TCS 最重要的实战模式,也是源码里出现频率最高的用法。 场景:老式硬件 SDK(很多消息中间件、串口 SDK 至今如此)只有回调 API:

改造前 · 只有回调的老 SDK
// 结果只能通过回调送出,调用方被迫嵌套、分散、难以组合
public class LegacyTemperatureSensor
{
    public void ReadTemperature(
        Action<double> onSuccess,
        Action<Exception> onError)
        => /* 内部发起硬件读取,结果走回调 */;
}
改造后 · TCS 桥接,调用端回归自然 async/await
public class TemperatureSensorBridge
{
    private readonly LegacyTemperatureSensor _sensor = new();

    public Task<double> ReadTemperatureAsync()
    {
        var tcs = new TaskCompletionSource<double>();   // ① 开一张空白欠条

        _sensor.ReadTemperature(
            onSuccess: value => tcs.SetResult(value),   // ② 成功回调 → 销账
            onError:   ex    => tcs.SetException(ex));  // ③ 失败回调 → 记坏账

        return tcs.Task;                                // ④ 欠条交出去,任何人可 await
    }
}

// 调用端:从此和普通异步方法毫无区别
double temp = await bridge.ReadTemperatureAsync();
Console.WriteLine($"当前温度 {temp}℃");

注意 ①:欠条开出来之后、回调到达之前,整个系统没有任何一条线程在等待或睡眠。 等待的成本是零——这正是欠条模型与"开线程干等"的本质区别。

面试高频为什么不直接 Task.Run 包一层?

有人会写 Task.Run(() => { 手动等回调完成 })——这是用一条线程池线程去睡觉等回调, 白白占用资源,还引入同步等待的死锁风险。TCS 方案零线程、零阻塞。 面试被问"Task 和线程什么关系"时,这句就是标准答案的核心: Task 是对未来结果的凭据,不是线程;一个 Task 的完成可以完全不占用任何线程。 深度解释见 Stephen Toub 的 Async/Await FAQ。

提前埋一个坑位(第 0003 课引爆)

上面的模板有个隐患:如果硬件永远不回调,这张欠条就永远悬挂, 调用方 await 到天荒地老,连携带的引用都释放不掉。解法是超时兜底—— .NET 6+ 一行 task.WaitAsync(TimeSpan),或手写 TCS+Timer。这是下一阶段的主菜。
