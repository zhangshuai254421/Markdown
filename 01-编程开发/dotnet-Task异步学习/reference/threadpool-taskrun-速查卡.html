线程池与 Task.Run 速查卡

来源:第 0008 课 主推阅读:Cleary · Task.Run Etiquette

一句话:线程池是"短平快 CPU 活"的经济系统—— 凡占着工人不还的用法都在放血。判决尺第一问:真正干活的是谁?

一、判决尺

活的本性真正干活的姿势典型例子
CPU-bound本机 CPUUI 场景 Task.Run 挪走防卡界面;服务端原地算压缩、序列化、图像、算数
IO-bound外部设备/远端真异步 API + await(0 线程)HTTP、磁盘、DB、定时

二、Task.Run 用 / 不用清单

✓UI 应用里跑 CPU-bound 短活(防界面冻结)
✓批处理/后台工具里做并行分片(有意识控制并发数)
×不包同步 IO——工人干等,慢性放血;找真异步 API
×库代码不用——并发的决定权在应用层(etiquette)
×ASP.NET Core 服务端不用——请求已是池工人,挪 = 多付开销
×不做 sync-over-async 糖衣——Task.Run(() => FooAsync().Result) 烧两个工人

三、线程池结构(讲得出才算懂)

部件一句话课程钩子
全局队列非池线程发起的 Task.Run 排这里0005:WaitingToRun
本地队列池线程内再排的活;含"偷活"(work stealing)细节可问老师
工人循环取活 → 干 → 还 → 取下一个0005:Running
补充机制全忙时约半秒注入 1 个新线程;可 SetMinThreads 调底数补充慢 → 饥饿的机械原因

四、烧工人账本(sync-over-async 三档)

写法工人占用结论
await 真异步 IO0✓ 唯一正确姿势
Task.Run 包同步 IO1(干等)× 放血
Task.Run(() => Async().Result).Result2(一个陪绑)× 仅迁移期过渡

五、诊断链(0005 → 0008 闭环)

1. 日志见 WaitingToRun 堆积→ 2. 找被占死的工人(Running 干等/卡死)→ 3. 揪出包 IO 的 Task.Run 或 sync-over-async

六、ValueTask 三纪律 + 选择表

①只能 await 一次(不缓存复用、不并发 await)
②完成前不混用(await 前后别拆 AsTask() 两头用)
③仅"高频 + 常同步完成"热路径;一般 API 用 Task
Task<T>ValueTask<T>
本体class(分配)struct(栈上)
同步完成仍分配 Task零分配(包结果)
消费任意次仅一次
默认✓仅热路径

七、术语表增量

线程池 worker运行时养护的可复用工人线程;循环执行池任务
饥饿 starvation工人被干等型任务占死,补充(约 0.5s/个)追不上排队速度
IO-bound / CPU-bound活的本性二分:外部设备干活 vs 本机 CPU 干活——判决尺第一问
work stealing本地队列的互补机制:空闲工人从别的工人本地队列"偷活"
ValueTaskstruct 欠条:同步完成零分配;代价是只能消费一次
sync-over-async同步阻塞等异步欠条(0007 死锁温床,0008 放血账本)

八、面试自测五问

① 为什么说 await 的 IO 是"零线程"? 真异步 IO 由设备/OS 完成并回调,期间无任何线程在等——欠条机制(0001 起)的全部意义。占线程的是"同步等待",不是 IO 本身。
② WaitingToRun 堆积,下一步查什么? 查被占死的工人:Running 卡死、干等的 Task.Run、sync-over-async。状态 → 池 → 代码姿势,三步闭环。
③ 服务端为什么不该 Task.Run? ASP.NET Core 请求本就跑在池工人上;Task.Run 只是把活挪个位置,还多付调度开销,降低吞吐。
④ ValueTask 为什么快?代价是什么? struct 包结果,同步完成路径零分配。代价:只能 await 一次、完成前不混用——违反即未定义行为。
⑤ 线程池饥饿时加线程为什么救不了急? 补充速率约每半秒一个,而干等任务占用是长期持锁——补充追不上消耗;根治靠改代码姿势,不是调参数。
