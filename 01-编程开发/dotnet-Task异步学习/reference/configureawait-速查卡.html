ConfigureAwait 与死锁速查卡

来源:第 0007 课 主推阅读:Toub · ConfigureAwait FAQ

一句话:死锁 = 循环等待;破环断一环即可—— 不阻塞(一路 async)或不回环(ConfigureAwait(false))。

一、上下文一览:你在哪个环境,await 恢复去哪

环境SyncContextawait 默认恢复ConfigureAwait(false) 后
控制台 / Windows 服务 / ASP.NET Corenull内联在完成者/线程池线程行为相同(无快递员可省)
WinFormsWindowsForms…ContextBeginInvoke 回 UI 消息循环在线程池恢复;更新控件需自行调度回 UI
WPFDispatcher…ContextDispatcher.BeginInvoke 回 UI 线程同上
ASP.NET classic(Framework)AspNet…Context请求上下文内串行推进在线程池恢复,但HttpContext.Current 等请求上下文丢失——库要留逃生口

二、死锁环(默画用)

节点在等谁
① UI 线程(卡在 .Result)② 外壳欠条完成
② 外壳欠条③ 续延(段 2)跑完才能 SetResult
③ 续延④ 被 Post 进 UI 消息队列,要求回 UI
④ UI 消息队列① UI 线程泵消息——但它正阻塞

成立条件与破环点

同时要有:同步上下文(UI / classic ASP.NET)+ 同步阻塞(.Result/.Wait) + 被阻塞线程正是上下文要求的恢复处。三者缺一不死锁。 破环:①改 async(不阻塞)或 ③改 ConfigureAwait(false)(不回环)。

三、三条纪律

①类库代码一律 ConfigureAwait(false)——不依赖调用方上下文,根除死锁,省一次 Post
②应用代码一路 async 到底——事件处理器用 async void(框架设计如此),绝不 .Result/.Wait()/GetAwaiter().GetResult()
③遗留同步边界用"隔离"——换同步 API,或放到无上下文的专门线程/进程;不要在 UI/请求线程上裸阻塞

四、ConfigureAwait 三个事实(面试精确度)

作用范围只作用于写它的那一次 await;不传染方法、不传染程序集
改变什么仅续延的恢复位置;结果/异常/取消语义原样(0005/0006 机制不变)
用在哪库代码写 false;UI 事件处理器不写(要回 UI);无上下文环境写不写等价,库仍惯例写

五、偏方与危险写法鉴别

写法后果判断
task.Result / task.Wait()UI/classic 上下文:死锁;无上下文:阻塞线程池工人禁止(应用层)
task.GetAwaiter().GetResult()与 .Result 同样阻塞/死锁;区别只是异常不包 AggregateException禁止(应用层)
Task.Run(() => FooAsync().Result).Result不死锁(内层无上下文)但 sync-over-async,烧两个线程迁移期过渡,留 TODO
async void(事件处理器以外)异常逃出欠条体系,崩溃进程或静默吞掉(0001 的 async void 坑)仅限事件处理器
ConfigureAwait(false) 后更新 UI 控件不在 UI 线程,跨线程异常需自行调度回 UI

六、术语表增量

SynchronizationContext"回调送到哪个环境执行"的调度约定;核心方法 Post(排队)/ Send(立即)
上下文捕获 captureawait 挂起时记下 SynchronizationContext.Current;恢复时非空则 Post

七、面试自测五问

① 为什么 .Result 在控制台不死锁,在 WinForms 死锁? 控制台 SyncContext 为 null:续延内联在完成者线程,欠条照常完成。WinForms 捕获 UI 上下文:续延排队等 UI 线程,而 UI 线程正被 .Result 阻塞——环闭合。
② ConfigureAwait(false) 写一处管整个方法吗? 不。只管写它的那一次 await;每个 await 独立捕获/不捕获。
③ 库代码为什么一律 false?会丢什么? 不依赖调用方上下文,根除死锁并省调度。代价:失去环境上下文——classic ASP.NET 的 HttpContext.Current、UI 线程亲和,都需要调用方自己处理。
④ Task.Run(() => Async().Result) 为什么"能跑"? 内层运行在无上下文的线程池线程:捕获不到 UI 上下文,环缺一环。但仍是 sync-over-async——烧两个线程,治标不治本。
⑤ UI 事件处理器能用 ConfigureAwait(false) 吗? await 之后要更新控件的不要用(需回 UI);纯计算/纯请求且不再碰 UI 的写 false 也没错——但应用层惯例是从简不写。
